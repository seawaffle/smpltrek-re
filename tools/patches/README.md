# Offline section patch builder

`patch_builder.py` appends one `sect` to the official **SmplTrek 3.2.174 system-only update** and
repoints `AppSystemInfo` primary vtable slot 15 (`draw_title`) to the payload entry. It emits a new
update and an exact, self-contained JSON recipe. It has no device access. Other versions, modified
source images, and content/BOOT/MCU updates are rejected; there is no source-hash override.

## Inputs

- Official `.bin` or `.zip` containing exactly one update. The hash pins the extracted `.bin`.
- Already linked, self-contained raw payload binary. Link it at the chosen load address. Resolve all
  symbols/relocations before extracting the binary. Raw binaries carry no relocation information, so
  the builder cannot check that linking was done correctly. Include any padding/zero storage in the
  payload; this tool does not run a C runtime, initialise BSS, or relocate code.
- Placement JSON, containing `load_address` (32-byte aligned), `entry_offset` (an even byte offset
  inside the payload), and `reserved_region` with inclusive `start`, exclusive `end`, and `evidence`.
  Addresses use lowercase `0x` plus eight hex digits. Offsets use JSON integers.

For example, this is a **format illustration using the candidate address 0xC3F00000 (claim EXE-4), not a placement
shown to be free on the unit**:

```json
{
  "load_address": "0xc3f00000",
  "entry_offset": 0,
  "reserved_region": {
    "start": "0xc3f00000",
    "end": "0xc4000000",
    "evidence": "Replace with the reviewed placement rationale and runtime checks for this experiment."
  }
}
```

Claim EXE-4 (`docs/07-ram-allocation.md`) identifies `0xc16ffa98..0xc4000000` as statically unclaimed DDR. Placement is restricted to that
candidate gap, must fit the explicitly declared region, and must not overlap loaded sections.
The evidence note is a recorded assertion by the caller, **not proof that RAM is free**. Hidden heaps,
stacks, computed-address users, and bootloader limits still require investigation. The builder does
not establish device acceptance of an extra section or compliance of payload machine code with the ABI.

## Commands

From the repository root, put generated artifacts under the gitignored `work/` directory:

```sh
python3 -B tools/patches/patch_builder.py build \
  "firmware/smpltrek/SmplTrek v3.2.174.zip" \
  work/payload.bin work/placement.json \
  work/patched.bin work/patch.recipe.json

python3 -B tools/patches/patch_builder.py verify \
  "firmware/smpltrek/SmplTrek v3.2.174.zip" \
  work/patch.recipe.json work/patched.bin

python3 -B tools/patches/patch_builder.py replay \
  "firmware/smpltrek/SmplTrek v3.2.174.zip" \
  work/patch.recipe.json work/replayed.bin
```

Create parent directories beforehand. Build/replay refuse to overwrite any file, including the
source. Build verifies the generated bytes before writing either artifact. Replay needs only the
source and recipe; the complete appended header and payload are embedded as hex.

## Exact change policy

The source SHA-256 is
`3b6848b0f041bcf23c73d4b0357d2f3d6dc9e7e03752b32ff7322e91e6814e53`, length `0x1dcf91`.
The builder resolves the slot through the section map and asserts its known file offset and old target.
All numbers in the following table are file offsets; each existing-field edit is four bytes.

| Offset | Edit |
| --- | --- |
| `0x04` | Container length increases by 12 + payload length |
| `0x08` | Container CRC, recalculated after the system CRC |
| `0x2c` | System descriptor length increases by the same amount |
| `0x34` | Internal system length increases by the same amount |
| `0x38` | System CRC |
| `0x50` | Section count 7 to 8 |
| `0x1cbf9c` | `a06d66c1` (target `0xc1666da0`) to little-endian payload entry address |

At original EOF, append `sect`, little-endian load address and payload length, then the exact payload.
No implicit padding is inserted. Versions, boot entry, image count, existing section placement and all
other original bytes must remain unchanged. The new section has no execution-permission flags in this
container format; calling the payload is controlled by the one vtable pointer.

The recipe (`sonicware-section-patch/1`) records source hash/length/version/profile, payload hash/length
and placement, hook identity, all seven replacements as offset/old_hex/new_hex/reason, an append record,
and output hash/length. Records include all four bytes even when some bytes within a field are unchanged.
There are no timestamps or machine-specific paths, so identical inputs produce identical artifacts.

The verifier replays edits and separately checks the parsed structure, immutable bytes, pointer target,
placement, payload hash, output hash and both CRCs. Valid CRCs alone cannot permit unrelated changes.
A recipe is an integrity/conformance record, not an authenticated signature or proof of safe payload behavior.

## Tests and first payload

```sh
python3 -B -m unittest discover -s tools/patches -v
```

Synthetic fixtures exercise generation, replay, malformed recipes, placement bounds, preservation,
valid-CRC unauthorized edits, hash failures, and CLI output handling. An optional corpus test checks the
actual official image, entirely in memory. Test payloads are arbitrary bytes and must never be flashed.

A first executable payload should preserve the drawing callback's arguments and return address and
tail-branch to its original target `0xc1666da0`. Later code must preserve the stock ABI (including B14),
handle caches appropriately, and account for repeated redraws. The builder itself creates no executable
payload and performs no hardware run. The pass-through and drawing probes run on the unit (device sessions S2
and A4 in `experiments/README.md`; EXE-1, EXE-2) are not published; their placement and cache limits (EXE-4, `docs/07-ram-allocation.md`)
still apply to any hardware experiment.

## Sterilised Lofi-12 XT image (`sterilise_lofi.py`, device session C3)

`sterilise_lofi.py build <official Lofi-12XT_v1.5.205 .zip|.bin> <output.bin> <recipe.json>` writes the
image run on the unit in C3 (2026-11-11): the two 16-bit instructions at the entry of `settings_save` (0xC2C8B0F8,
file offset 0x11FAC4) become `mvk .L1 0,a4; bnop .S2 b3,5`, the family word becomes 5, and both CRCs are
resealed with the SmplTrek seeds. The source hash, the entry bytes and the compact packet header are
asserted before anything is changed; `verify` replays the recipe. Thirteen bytes differ from the official
file. Why this form and not three 32-bit instructions: `docs/01-platform-map.md`, "Where the patch has to
fit". Check every built image by disassembly (`analysis/mmtd2elf.py`, then `tic6x-elf-objdump -d`,
diffed against `work/lofi-1.5.205.dis`) before it goes on a card; the hashes, preconditions and result
are in `experiments/README.md`, "C3 sterilised Lofi-12 XT image".

## Checking a sterilised CyDrums 1.1.84 image (`check_sterilised_cydrums.py`, session C5, run 2026-11-20)

Read-only; there is no CyDrums builder here. `check_sterilised_cydrums.py <official CyDrums_v1.1.84 .zip|.bin>
<candidate.bin> [--decode]` checks a locally built image against `docs/01-platform-map.md`, "The same patch fits
CyDrums 1.1.84": the official source (hash pinned), the entry 0xC24C4458 mapped through the section table to file
offset 0xACBF8, the same 16-bit pair as Lofi (`26 06 ef a1`) with the compact header `0xEBC00050` kept, family word
5, both CRCs valid under the SmplTrek seeds, and no other byte changed. `--decode` disassembles the entry's whole
fetch packet in source and candidate and requires every line but the two entry slots to read the same. A PASS says
nothing about device behaviour. Tests (`test_check_sterilised_cydrums.py`) build candidates in memory only.
