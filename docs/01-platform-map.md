# Platform map: SmplTrek, Lofi-12 XT, CyDrums

The three products run on the same board (TI C6748, same codec, panel controller, SPI flash, SD) and their
firmware shares a platform layer. This page records what is shared, what differs, and where each piece sits in
each product, so the platform can be understood once and read across all three. Reference images: SmplTrek
3.2.174, Lofi-12 XT 1.5.205, CyDrums 1.1.84 (other versions of each product are reached through their own carried
symbol files).

Status words: **verified** = compared instruction by instruction with constants kept (`region_diff.py`) or
read by hand in all three; **matched** = func_match paired the code (normalised bodies, constants hidden),
behaviour not compared; **open** = not checked yet. Dates in headings and text are when a finding was made.
Session codes (A4, C3, C4, C5, D0, D1, ...) name device runs recorded in [`experiments/README.md`](../experiments/README.md)
and `experiments/sessions/`; static and simulated findings say so.

## How to use this

- **Addresses are per product.** Never reuse a SmplTrek address in another image. Each product has its own
  symbol file in `symbols/` (generated by `carry_symbols.py` from the hand-written SmplTrek file), and
  `02-platform-symbols.md` lists every named symbol side by side.
- **Data-page (B14) offsets differ too.** The same global sits at a different B14 offset in each product
  (examples below). Code that touches a global must take the offset from that product's symbol file or
  from its own disassembly.
- **Checking a new claim across products:** `python3 -B analysis/region_diff.py START END` (SmplTrek
  addresses) disassembles the range in all three and reports moved data addresses, data-page offsets and
  real differences separately. `03-platform-shared.md` (`platform_map.py --shared`) runs it over every
  identically laid-out block.
- **Per-product findings that cannot be carried** (code compiled differently, product-only code) go in
  `symbols/hand/<product>-<version>.json`; `carry_symbols.py` merges them into the generated file.
- `region_diff.py --at LOFI CYDRUMS` compares from explicit starts when the layout differs; `--data N`
  also compares N bytes at every address constant (use the record size of the tables involved).
- When something here is checked further, update this page, and regenerate the two generated pages with
  `python3 -B analysis/platform_map.py` and `python3 -B analysis/platform_map.py --shared`.

## Image layout (verified)

| | SmplTrek 3.2.174 | Lofi-12 XT 1.5.205 | CyDrums 1.1.84 |
|---|---|---|---|
| Entry (`_c_int00`) | `0xC1694580` | `0xC2CD1AA0` | `0xC25F8CA0` |
| B14 (data page) | `0xC16F3320` | `0xC2DA6758` | `0xC26B0EC0` |
| Code (`.text`) | `0xC1505400`-`0xC16AD320` (1.66 MiB) | `0xC2B80C00`-`0xC2CEC8C0` (1.42 MiB) | `0xC2431C00`-`0xC2618280` (1.90 MiB) |
| `__TI_auto_init` | `0xC168673C` | `0xC2CC2000` | `0xC25E3780` |
| Zero-filled DDR from `0xC0000000` | to `0xC1503404` | to `0xC2B80904` | to `0xC24317EC` |
| Free-looking DDR gap after the image | to `0xC4000000` (41 MiB) | to `0xC3C00000` (14 MiB) | to `0xC3C00000` (21 MiB) |
| L1D RAM `0x11F00000` | 5.4 KiB zero-filled | 13 KiB initialised | 14 KiB initialised |

**On-chip memory and caches (2026-11-12).** `0x11F00000` is L1D (an earlier reading called it L2 SRAM): the C6748 has L1P at `0x11E00000` and L1D
at `0x11F00000` (32 KiB each) and L2 at `0x11800000` (256 KiB), per StarterWare's evmC6748 linker files. The SYS/BIOS
cache start-up (SmplTrek `0xC1677EE0`, Lofi-12 XT `0xC2CAE8A0`, CyDrums `0xC25CC5A0`; entry 6 of SmplTrek's
`g_startup_fxns`) was run in `analysis/c6sim.py` and writes the same values in all three. Decoded with TI SPRUFK5A
(C674x megamodule) Tables 2-2, 3-2 and 4-4:
- L2CFG = 4: 256 KiB L2 cache, so all of L2 is cache and none is RAM;
- L1PCFG = 4: 32 KiB L1P cache (all of it);
- L1DCFG = 3: 16 KiB L1D cache. L1D cache is taken from the top of L1D downwards (SPRUFK5A 3.1), so
  `0x11F04000`-`0x11F07FFF` is cache and `0x11F00000`-`0x11F03FFF` is RAM. Every product's on-chip data (the audio
  DMA buffers and blocks above, at most 14 KiB) lies in that 16 KiB;
- MAR registers with PC (cacheable) set: 17 (`0x11000000`-`0x11FFFFFF`), 128 (`0x80000000`-`0x80FFFFFF`, the
  shared RAM) and 192-199 (`0xC0000000`-`0xC7FFFFFF`, the 128 MiB DDR).
So the app has 16 KiB of fast on-chip RAM, all of it used, and runs everything else from cached DDR. No on-chip
memory is left over: any other user would have to take it from these buffers or shrink a cache (inference).

Same section structure in all three (seven load sections: three small high ones, `.text`, a small one below
`.text`, constants, data). The gap rows come from `memory_map.py` and are not proven free (heaps and task
stacks are invisible to it). The images load at different addresses, which the bootloader's section loader handles.

## How much is shared

From `03-platform-shared.md` (lower bounds: shared means func_match paired it in both other products):

- 16% of SmplTrek's code bytes (2282 of 8581 functions) are matched in both Lofi-12 XT and CyDrums.
- The hardware and library layer is shared almost completely: HAL classes 15/15, StarterWare McASP/EDMA3
  67/70 named, SPI flash driver 14/14, codec setup 5/5, FatFs 18/20, MIDI classes 26/28, SoundOSC 27/30,
  Graphics 2/2, C++ ABI 6/6.
- The sound design is product-specific: SoundEffect 12/126 functions, SoundEngine 11/79, TrackSound 7/45,
  Voice 0/21, application classes 264/1430.
- 157 code blocks are laid out identically in all three (180 KB); 77% of those bytes differ only in data
  layout, the rest have real differences (listed per block in `03-platform-shared.md`).

| | Status | Notes |
|---|---|---|
| Physical buttons and bit map | **verified same** | The factory button-test page (`AppTestControl::draw`) draws the same panel in all three: Lofi-12 XT runs identical code and identical rectangle tables; CyDrums' copy is compiled differently but encodes the same coordinates, bit numbers and bit-mask tables (compared helper by helper). | Held-switch word | **verified same place** | `g_control_switch_state` = scanner+64 in all three (SmplTrek `0xC1501DF0`, Lofi-12 XT `0xC2B7D6C8`, CyDrums `0xC242E8E0`), so the button state is read the same way on every product. |
| Switch poll (`control_switch_poll`) | **same algorithm, read by hand** | Lofi-12 XT `0xC2C86540`, CyDrums `0xC259F9E8` (hand symbols). Same steps; compiled differently, and the hardware-source pointer is at scanner+24 instead of +20. |
| Key matrix (`ControlScan`) | **verified identical** | The scanner's hardware source is a GPIO key matrix, not the panel MCU: `ControlScan::select_row` drives GP2[0..5] one row at a time (`gpio_clr_data(1, 0x3F)`, `gpio_set_data(1, 1 << row)`), `ControlScan::scan` reads the columns GP3[1..6], GP3[9], GP3[11] (plus GP5[10], active low, as bit 4 in row 0), and `control_switch_poll` merges each row at bit `8 * row`. So switch bit n = row GP2[n / 8] x column n % 8 (columns GP3 1, 2, 3, 4, 5, 6, 9, 11); 6 rows x 8 = bits 0-47. | Pad velocity lookup (`pad_velocity_from_curve`) | **same algorithm** | Body similarity 0.94 (Lofi-12 XT) / 0.96 (CyDrums). |
| Pad sensor processing (`pad_sensor_update`, hard-hold tracker) | **product-specific** | Lofi-12 XT keeps SmplTrek's hold tracker (same functions) but its sensor update is a different, larger function (250 vs 163 instructions); CyDrums has no counterpart for either. |
| Panel-controller protocol | **verified same** | `ADControllerUART::parse` is identical in all three. `0xBn lo hi`: analogue channel n (0-15), 14-bit value `lo \| hi << 7` (7-bit bytes), stored at uart+36+2n and sent to the delegate's slot 1 `(delegate, uart, channel, value)`. `0xA1` + six 7-bit bytes: stored at uart+70..75, no callback; bytes 3-5 (+73..+75) are the panel MCU firmware version shown as MCU on SYSTEM INFO (`mcu_version_string`, same code in all three, '*.*.*' while +73 is 0xFF), bytes 0-2 have no reader in any of the three (2026-11-10, rechecked: no address constant for uart+70..72 and no load at those offsets; a computed-index read is not excluded). Channel 15 (uart+66) is the battery voltage (see "Power management"). Every byte received while idle also goes to delegate slot 0 `(delegate, uart, byte)`. |

Press/release thresholds are the same in all three products' sensor code (800 / 100); release debounce is 4 samples in SmplTrek and Lofi-12 XT, 10 in CyDrums. Processed pad events (press/release with velocity, hard hold) go through the single word `g_pad_delegate` (= g_pad_sensor+124 in SmplTrek `0xC1500560`, +1024 in Lofi-12 XT `0xC2B6A100` and CyDrums `0xC241BF40`; same writers: MainDelegate+40 and a test page). |
| Encoder hardware read | **verified identical** | Five encoders on GPIO. `encoder_read_phases` (reads GPIO banks 3 and 5 through `gpio_read_bank16`, packs two quadrature bits per encoder: encoder i = `(word >> 2i) & 3`) and `gpio_read_bank16` are identical in all three (region_diff, 0 differences). `encoder_pinmux_init` writes the same PINMUX7/11/12 masks everywhere, and `pupd_set_19_20(0)` is byte-identical. | Encoder decoding | **differs** (see below) | SmplTrek: plain code, no acceleration. Lofi-12 XT and CyDrums: `RotaryEncoderV2`, speed-dependent step size. |
| Encoder delivery | **differs** | SmplTrek 3.2.174 delivers encoders through MainDelegate's RotaryEncoderDelegate (`post_encoder_event`, message `{type 4, encoder, delta}`) to controller slot 7 `(encoder, delta)`; Lofi-12 XT's `RotaryEncoderV2` calls the delegate with the same `(encoder, delta)` shape. ### Pad processing and board pins compared for a cross-flash (2026-11-11)

Static, SmplTrek 3.2.174 against Lofi-12 XT 1.5.205 (CyDrums where noted), done before device session C3
(a Lofi-12 XT app run on the SmplTrek, [`experiments/sessions/C3-crossflash.md`](../experiments/sessions/C3-crossflash.md)).
The question is whether a Lofi-12 XT app on SmplTrek hardware reads the pads correctly and drives the board the way
SmplTrek does.

**Pad sensor processing** (`pad_sensor_update`, SmplTrek `0xC16576F0`, Lofi-12 XT `0xC2C69F54`, read by hand).
- Same input: called per channel 0-14 from `on_pad_analog` with the 14-bit panel value (table above).
- Same press and release logic: press at a raw value of 800 or more, release below 100 debounced over 4 samples,
  velocity from the same three curves (`pad_velocity_from_curve`), events to the pad delegate's slots 0-2,
  the hold tracker (`pad_hold_start` / `pad_hold_reset`) as in SmplTrek.
- What Lofi-12 XT adds (why it is 250 instructions, not 163): a 52-byte per-pad record (`sensor + 52*ch`) and a
  fourth delegate slot (vtable +12) carrying continuous pad pressure. Decoded and simulated 2026-11-19 (section
  "Hardware use per product"): a 40-sample countdown from the press sets a baseline, raw > baseline + 200 turns
  pressure on, and the pressure is the mean of the last 9 curve-3 lookups / 127 (divide by 9.0f, `0x41100000` at
  `0xC2C6A0E4`; not an 8-sample average as first read), sent when it moves by more than 1/127.
- So Lofi-12 XT reads the same values the same way and derives more from them. The panel MCU on a SmplTrek is
  SmplTrek's (MCU 1.0.6); whether its pad scaling matches a Lofi-12 XT panel MCU is not known (no Lofi MCU image
  to compare). A mismatch would show as pads that feel harder or softer, not as a fault; C3 did not report on pad feel.
- What the pad code needs from the panel MCU (2026-11-14, static, all three products). Only the shared
  protocol.
  - App to MCU: each product has the same send routine (SmplTrek `0xC161E3C0`, Lofi-12 XT `0xC2C5C720`, CyDrums
    `0xC2577500`) and exactly nine places that reach it: the seven one-byte senders and `panel_led_command`. They
    sit at the same offsets, with the same reference counts (19 callers of `panel_led_command` in each).
  - Each product has a single function with the UART1 base `0x01D0C000` as a constant: the instance-to-base helper
    (`0xC1682F0C` / `0xC2CB93CC` / `0xC25DEE4C`, func_match counterparts). So no product sends the MCU anything the
    others do not, and none writes the UART outside that path.
  - MCU to app: the parser is identical (table above).
  - The product-specific `pad_sensor_update` uses only its own sensor record, the pad delegate, and the
    (channel, 14-bit value) it is handed. None of the three loads the UART object, the stored channel array or the
    A1 bytes.
  - All three assume the same value scale: press at 800, release below 100 (constants in each function), and the
    same velocity curves. Release debounce is 4 samples in SmplTrek and Lofi-12 XT, 10 in CyDrums.
  - Not checkable from the DSP side: whether a foreign product's MCU firmware scales the analogue values the same
    way. A difference would change pad feel, not function. Only a device run of a foreign app can show it.

**GPIO pins.** Every pin the three apps use goes through the shared helpers (`gpio_pin_number(bank, pin)`, a
direction wrapper over StarterWare's `GPIODirModeSet`, `gpio_write`). Compared in all three:

| `gpio_write` call sites, value constant | 46 (27 x 0, 17 x 1, 2 computed) | same | same |
| `GPIODirModeSet`, `GPIOPinWrite`, `gpio_set_data`, `gpio_clr_data` direct callers | 1, 2, 1, 1 | same | same |

`audio_gpio_init` had not carried to Lofi-12 XT or CyDrums because func_match didn't pair it; it is there, identical,
at the addresses above. So the three apps configure the same pins in the same directions and write the same
constants. What differs is product code deciding *when* to call `gpio_write` with a computed value; those two
computed writes (SmplTrek `0xC1671F50`, `0xC167203C`) are inside the 168-instruction block above, which is
identical. Not covered: pins reached without these helpers (none found: each low-level helper has the same
small caller count in all three), and the McASP pins (`McASPPinGPIOSet`, inside the matched McASP driver).

**Panel LEDs.** `led_set` (SmplTrek `0xC15F2A40`) sends `{0xC1, a, b, c, value}` through `panel_led_command`
(`0xC161E814`), which lies inside the panel code block already verified identical (`0xC161E3C0`-`0xC161E890`). So
the LED message format is the same. The LED setters themselves are also the same (2026-11-12, `panel_map.py`,
simulated): `pad_rgb_set`, its three 15-entry setter tables and the three clear-everything functions give the same
115 (a, b, c) addresses in all three products (map in 04-hardware-access.md, "Panel MCU on UART1"). Which page lights
which LED when is product code and was not compared.

**Memory during the hand-over.** The bootloader runs from `0xC7020000`-`0xC70B0000` (its loaded sections are
`0xC7074628`-`0xC70AEA60`; no address constant in it points into `0xC0100000`-`0xC6FFFFFF`; its four
`0xC0000000` constants are bases added to an argument). Every Lofi-12 XT load section is inside
`0xC2B809E8`-`0xC2DBC698`, so loading Lofi-12 XT cannot overwrite the running bootloader.

**Residual differences that static reading cannot settle.**
- PLL and DDR set-up come from SmplTrek's bootloader (AIS functions 6 and 3). A Lofi-12 XT unit has its own
  bootloader, not dumped. If its clocks differ, timing-derived rates (UART baud, the 1 ms tick) would differ
  between a Lofi-12 XT unit and a cross-flashed SmplTrek. Whether the codec's 24.576 MHz MCLK comes from the C6748
  or from its own oscillator is not traced (inference: an oscillator, "Clocks" below). In C3 the Lofi app recorded,
  played back and drove the panel and display on the SmplTrek with no problem reported; pitch and timing were not
  measured.
- Pad feel (panel MCU scaling, above). LED addressing is the same (above); what each page shows on the LEDs is not.

### Encoders: what selects RotaryEncoder versus RotaryEncoderV2

Nothing at run time. In Lofi-12 XT and CyDrums an `.init_array` entry (`encoders_static_init`) calls
`__cxa_vec_ctor(g_rotary_encoders_v2, 5, 36, RotaryEncoderV2::RotaryEncoderV2, 0)` unconditionally, and
`encoders_init` puts pointers to those five objects into `g_encoders`. `RotaryEncoder::RotaryEncoder` has no
call, no address constant and no data word pointing at it in either image (string_refs plus a scan of every
aligned word), so `RotaryEncoder` is dead code and the choice is made at build time, not by hardware revision
(an earlier guess). All three Lofi-12 XT
versions on file (1.1.156, 1.2.179, 1.5.205) have both classes; no SmplTrek version (1.0.65 to 3.2.174) has
them (RTTI).

SmplTrek's equivalent is non-virtual code with V1 behaviour: `encoder_update` on five 24-byte objects at
`g_encoders` (also built in static initialisation, `input_static_init` below). Lofi-12 XT's dead `RotaryEncoder::update` has the same instructions as it (region_diff `--at`:
82 vs 82 instructions, every difference is a field offset or branch offset).

|---|---|---|---|
| Encoder objects | `g_encoders` `0xC10E1288`, 5 x 24 bytes, inline | `g_rotary_encoders_v2` `0xC2B7B9A0`, 5 x 36 | `0xC242C820`, 5 x 36 |
| Array passed to the poll | `g_encoders` (the objects) | `g_encoders` `0xC2B7EF08` (5 pointers) | `0xC242FD70` (5 pointers) |
| Per-encoder update | `encoder_update` `0xC166D924` | `RotaryEncoderV2::update` `0xC2C90108` (vtable slot 0) | `0xC259BD70` |

| Static init (`.init_array`) | `input_static_init` `0xC16765E0`: `__cxa_vec_ctor(g_encoders, 5, 24, Encoder::Encoder)` (plain, no vtable) | `encoders_static_init` `0xC2C8FEC0` | `0xC259BAA0` |
| Acceleration table | none | `0xC2D989A0` | `0xC26A10F0` |

Behaviour (V1 simulated, `analysis/input_map.py`; V2 read from the listings; neither tested on hardware):
- **V1 / SmplTrek**: the first change after the rest position (phase 3) sets the direction (phase 1: -1,
  phase 2: +1); each arrival at phase 0 with a direction set adds one step, so one step per clean detent; the
  steps are reported every 16 polls if non-zero (not +1/-1 per quadrature change, as first read; details and
  bounce cases: `docs/04-hardware-access.md`, "Encoders").
- **V2 (Lofi-12 XT, CyDrums)**: one report per detent. The poll passes `tick_count()` as `now`. At the rest
  position the time is recorded; at the second change after it the step is
  `table[(now - t_rest) / 2]` = 12, 10, 8, 6, 5, 4, 3, 2, 1 for the first nine buckets, else 1, signed by
  direction. So a fast turn moves up to 12 per detent. With 1 ms ticks (section "Clock tick") the buckets
  are 2 ms wide, measured from reaching the rest position to the report: under 2 ms gives 12, 2-3 ms 10, ...,
  16-17 ms 1, and 18 ms or more also 1.

So encoder events in every product pass through a delegate (`post_encoder_event` in SmplTrek; slot 0 of the
RotaryEncoderDelegate in `+8` of each V2 object in Lofi-12 XT and CyDrums), but the values differ: SmplTrek reports
batched unit steps, the others report accelerated steps, and CyDrums wraps the step in a message. The raw phases are
the same everywhere: `encoder_read_phases` is the same code with the same bit layout in all three.

The panels are not physically different (an earlier assumption): all three products have the same buttons and
15 pads; what differs is how each app interprets pad data.

`audio_block_process` is the same code in all three (only constants differ, read side by side): it picks
the free buffers from EDMA PaRAM link fields (`0x01C04014`, `0x01C04034`), zeroes the float block, calls
the render callback, and converts `sample * 2^31` to int32 into the TX buffer.

**The render callback contract, common to all three:** the callback in that product's slot is called once per
block in Swi context with the block; `frames = block[1]` (word at +4), `L = block + 16`,
`R = block + 16 + 4 * frames`. It has 2.67 ms (SmplTrek) or 2.0 ms (the others) per call.

The "L" / "R" names of the two planes fit the stock's own input set-up: plane 0 is the even DMA words, and the
REC SRC sources put the left ADC there (`docs/04-hardware-access.md` "Channel order", claims HW-26 and HW-28).

The mixer behind the callback (`audio_render_main`, the effect racks, the tracks) is SmplTrek-only; the
other products' render callbacks are their own engines.

SmplTrek's mix routing (claim AUD-13, symbol file entries cited there; static reading, confirmed by the full engine
map and simulation in `docs/06-audio-engine.md`, claims AUD-1 to AUD-12): `audio_mix_main` clears
`g_post_bus` and `g_send_bus`, then `audio_mix_tracks` walks `g_track_table` (`0xC16ED728`, `TrackInterface *[15]`:
0-9 the sequencer tracks, set at run time, LOOP tracks switching between the two `g_loop_tracks` banks; 10-12 the
GLOBAL tracks; 13 USB AUDIO; 14 EXT SRC). Each track renders into `g_track_dry_block` and `g_track_send_block`
(vtable +12, then its pair of `g_mixer_channels`); the dry block is added into `out` and the send block into
`g_send_bus`. The send effect takes the send bus as input and writes the block `0xC16DE750`; a third block
`0xC16DF790` is the sidechain key (`0xC15AAAD0` is a getter for that key block, not a pass over the tracks).
`audio_mix_usb` and `audio_mix_ext` do the same for tracks 13 and 14 but put their dry output into `g_post_bus`, which
`audio_render_main` adds at unity after the effect stage, so USB AUDIO and EXT SRC skip the master effect and PROJECT
LEVEL. Per track, the audio passes through the TrackInterface render slot and the B14+1016 tap object (called after
every track with the dry block); the whole sequencer mix is `audio_mix_tracks`. While `audio_preview_active()`
(B14+495) is set, `audio_preview_mix` replaces the track mix. `0xC158C668` returns B14+532 directly; the 54-entry
table after it belongs to the next function.
Lofi-12 XT's `g_track_table` (`0xC2D827E0`) holds eight null entries, then its USBTrack (`0xC2B7E10C`) and ExtTrack
(`0xC2B7D7A8`) objects (constructors read; the same layout with 8 sequencer tracks). Its mix code was not read, so the
routing above is SmplTrek's only.

### Codec set-up and input switching (SmplTrek 3.2.174; static, 2026-11-11)

**Sources.** Read from the code at the addresses named here. The codec is a TI TLV320AIC3106 at I2C0
0x18 (`codec_write`; identity: every register the code uses is in the AIC3106 map, `docs/04-hardware-access.md`
"Codec identity"). Register meanings checked 2026-11-12 against the AIC3106 data sheet (SLAS509G, Rev. G, section
10.6), and every function below simulated in all three products with `analysis/codec_map.py` (identical writes);
the text below gives the checked readings. The full decoded table is in 04-hardware-access.md,
"Audio". The codec functions are a modified copy of TI StarterWare's `examples/evmC6748/mcasp/aic31.c`. The symbol file has every
function's evidence. The codec functions (`0xC161D560`-`0xC161DF84`) were already shown to be identical
code in Lofi-12 XT and CyDrums (table above), and all new names carry to both. `audio_gpio_init` and the
GPIO roles below were read in SmplTrek only.

**Start-up order.** `audio start` (`0xC1621574`) sets the I2C slave address to 0x18, then:
1. `codec_i2c_init` runs these steps:
   1. `codec_reset`: register 1 = 0x80.
   2. A one-tick wait.
   3. `codec_set_audio_interface(0, 32, 0)`: register 9 = 0x37 (I2S, 32-bit words, re-sync) and register
      10 = 0.
   4. `codec_set_sample_rate(48000)`.
   5. `codec_input_init`.
   6. `codec_output_init`.
2. If its argument is set, register 12 = 0x50 (ADC high-pass on).
3. `mcasp_configure`, then `audio_start_transfers`.

**Clocks.**
- The codec is the clock master: register 8 = 0xD0 drives the bit and word clocks, matching McASP's
  external clocks.
- The PLL runs with P = 2: for 48 kHz, J = 8 and D = 0; for 44.1 kHz, J = 7 and D = 3500. Register 7 (0x0A / 0x8A)
  is the datapath register, not part of the PLL: bit 7 selects fs(ref) 48 / 44.1 kHz (AGC timing) and bits 4:1 send
  left data to the left DAC and right to the right (SLAS509G Table 10-15).
- What the arithmetic fixes is the codec's **input** clock. With R = 1 (register 11 not
  written) and PLLCLK_IN = MCLK (register 102 not written), fs(ref) = MCLK x K / (2048 x P) gives 48 kHz and
  44.1 kHz only for MCLK = 24.576 MHz (TI's EVM example uses the same MCLK with P = 4, J = 16). The source of that
  clock isn't seen in code (inference: a 24.576 MHz oscillator; the DSP's 24 MHz would give 46.875 kHz).
- Register 8 = 0xD0 also sets bit 4: the bit and word clocks keep running while the codec is powered down.
- The 44.1 kHz branch exists, but the only caller asks for 48 kHz.

**Run-time rate trim.** `codec_set_pll_fraction(trim)` rewrites J and D, so the rate becomes
48 kHz × (1 + trim / 80000). A loop next to `audio_clock_probe_tick` (`0xC1661080`, `0xC16612E0`):
- measures Timer64P1 (0x01C21000);
- steps the trim in units of 300 while the byte at B14+560 is set.

The reference is the DSP's own crystal, not USB, SYNC IN or MIDI clock (2026-11-12, static). The loop
is armed (`0xC1661230`, TIMER64P1 started, B14+560 set) by the USB audio class code when a streaming interface is
active and disarmed (`0xC16612E0`) when both are idle; IOObserver calls `0xC1661080(tick_count)` about once a
second and it corrects at most every 10 s from the per-second TIMER64P1 counts. TIMER64P1 runs from PLL0_AUXCLK
(SPRUH79 Table 7-1), the 24 MHz crystal. Details in 04-hardware-access.md, "Audio for a firmware: paths, sequence,
pop-free order, unknowns".

**Output.** `codec_output_init` powers both DACs and routes them through DAC_L3/R3 straight to the
LEFT_LOP and RIGHT_LOP line drivers at 0 dB (registers 37, 41, 42, 86, 93). Functions that set headphone-driver
routing and levels (registers 47-71) exist: `0xC161D798`, `0xC161D7D4` and `0xC161D7E8`. So do
line-out level functions (`0xC161D758`, `0xC161D894`). But their one-line wrappers (`0xC1678670`-
`0xC1678728`) have no caller or stored pointer (searched for direct calls and pointer words) in any SmplTrek from
1.0.65 to 3.2.174, in Lofi-12 XT 1.1.156 to 1.5.205 or in CyDrums (claim HW-15). Register 41 = 0x50 selects the
DAC_L3/R3 paths straight to the line drivers, so the DAC_L1/R1 mixer routes these functions set would carry nothing
anyway. So the headphone drivers keep their reset state (off), and the headphone jack and speaker must be fed some
other way, from the line outputs or by an amplifier on the board (not identified in code). ELZ_1 play 3.1.149, by contrast, drives all four headphone drivers
from DAC_L1/R1 (its own output set-up). Manual: a VOL knob sets headphone/speaker level and plugging headphones in
turns the speaker off, with no code path found (inference: VOL pot and amplifiers after the line outputs, and a
switched jack).
`codec_set_dac_mute` (registers 43 and 44: 0x80 muted, 0 for 0 dB) runs from the power-message handlers
and the factory test-audio page.

**Input.** `codec_input_init` routes LINE1L to the left ADC and LINE1R to the right ADC, fully
differential at 0 dB, with MIC3 off. `codec_adc_hpf_init` loads a first-order DC blocker into both ADCs'
programmable high-pass filters (page 1: N0 = 32725, N1 = −32725, D1 = 32682, about 20 Hz) and enables
them (register 107 = 0xC0).
- **Built-in mic:** `codec_route_mic3r_to_left_adc` and `_right_adc` switch one MIC3R input into both
  ADCs. That fits the manual's mono built-in mic (inference).
- **Gain:** the PGAs (registers 15 and 16) take 0.5 dB steps through `codec_set_pga_left` and
  `codec_set_pga_right`.

**Board switches.** `audio_gpio_init` (`0xC1649320`) resolves 13 GPIO pins:

Sizes are the memcpy lengths in each validator (memcpy byte-matched to the TI runtime). Same tags, same
two-tag 4 KiB image and same storage sectors; the PREF payload differs in size, so a settings
block must never be copied between products. The field layout per product is in "PREF fields" below.

PREX (read 2026-11-10): Lofi-12 XT's and CyDrums' validators never read the second half of the block. On both
paths (tag match or not) they store the 'PREX' tag and constant defaults into `g_settings_ext` (stores up to at
least +116), then clamp the PREF fields; no 0xC00 offset is formed anywhere in either validator, and the shadow
copy at the end covers PREF only (404 / 376 bytes). SmplTrek's validator is the only one that loads PREX from
flash. So in Lofi-12 XT and CyDrums the PREX half is written but never read back. SmplTrek's PREX content (2026-11-10,
see `g_settings_ext` in the symbol file): the USB AUDIO track settings at +4 and the EXT SRC track settings at +56 (same
layout, 52 bytes each, labelled in "PREF fields" below), a smaller block at +108 (inference: the EXT SRC audio file) and a word at +364; those two
are not labelled.

Writer (read 2026-11-10, the same in all three apart from the sizes in the table): `settings_save` first calls
`settings_changed`, which compares `g_settings` and `g_settings_ext` with their shadow copies and returns 0 when
nothing changed; then nothing is written. Otherwise, for 0x01FFF000 and then 0x01FFE000, it erases the 4 KiB
sector (`request_erase(driver, sector, 4096, -1)`, one 0x20 sector erase) and calls `settings_sector_write_verify`
twice, at sector+0 with `settings_pref_fill` and at sector+0xC00 with `settings_prex_fill`. The helper clears its
buffer, lets the fill callback memcpy the struct in (tag word included, it is word 0 of the struct) and return the
length, programs bytes 4..len-1, reads them back to buffer+4096 and compares, and only then programs the 4-byte tag.
No retry. So each saved half is the struct followed by erased flash (0xFF), and the tag is written last: a save
interrupted before the tag leaves a half without a valid tag. SmplTrek's `settings_validate` then returns -1 and
`settings_load` validates the copy at 0x01FFE000, which is written only after 0x01FFF000 is complete. Lofi-12 XT's
and CyDrums' validators return the same way (0 on a tag match, -1 otherwise).
- **What follows SmplTrek's 284 PREF bytes:** 0xFF up to +0xC00. A cross-flashed Lofi-12 XT copies SmplTrek's 284
  bytes plus 120 bytes of 0xFF into its 404-byte `g_settings` (then clamps the fields); CyDrums would copy 92 bytes
  of 0xFF.
- **Lofi-12 XT's and CyDrums' PREX half:** 380 bytes of their `g_settings_ext` (defaults at boot plus whatever the app
  changed before the save). A cross-flashed SmplTrek reads the PREX half (it is the only reader): it would copy
  372 of those 380 bytes and clamp what it knows. The meanings of Lofi-12 XT's and CyDrums' PREX fields are not
  mapped.

Naming notes (symbol files, 2026-11-10):
- `HAL::FlashMemoryDriver::request_erase` is `0xC15DFA64` (posts request type 3 without a buffer, sent to `do_erase`)
  and `request_program` is `0xC15DF988` (type 2 with a buffer, sent to `do_program`); the two were swapped in the
  symbol files of 2026-11-09. The writer's change check is `settings_changed` (once named `settings_block_build`).
  The four write call sites and XF-2 are unaffected.
- `carry_symbols.py` swapped `g_settings_ext` and `g_settings_ext_tag` in the carried Lofi-12 XT 1.5.205 and 1.2.179
  files, and pointed 1.1.156's `g_settings_ext_tag` at the struct, because those validators load
  `g_settings_ext + 0x174` before `g_settings_ext` (data symbols are carried by the position of address constants in
  matched functions, which breaks when the compiler reorders constant loads). The hand files for all three versions
  name the tags, `g_settings_ext` and `settings_validate` (PREF sizes 344 / 356 / 404 bytes in 1.1.156 / 1.2.179 /
  1.5.205).
- Every "value is 1 or 3" MIDI gate has the same body, so `carry_symbols.py` named Lofi-12 XT's OUT TO DIN test
  (`0xC2BCF1EC`) `midi_rx_command_enabled` in 1.5.205 and 1.1.156; their hand files override it. The other carried
  MIDI gates in Lofi-12 XT 1.5.205 and CyDrums were checked against the page rows and are right. Carried names of
  these small gates in other versions without a hand file are unchecked.

Each setting is read through the product's getter, or at `g_midi_settings + offset` from this table; the gates
answer "is MIDI X enabled" the same way in all three.

  `0x02297EC0` at `0xC2BD343C` and `0xC2BD3444`, helpers [1,130] and [0,1]).

So the SYSTEM page's SOURCE, POLARITY IN/OUT, SPEAKER MUTE, metronome volume, precount and pad velocity sit at the
same offsets in all three (ranges differ for precount and pad velocity). From the 8-word array to TEMPO LED, Lofi-12 XT
and CyDrums have SmplTrek's fields four bytes later (array, MIDI channels and CONFIG, battery type, auto power off,
tempo LED, and SmplTrek's +0x10C [0,127] d=100 at +0x110); which earlier field accounts for the shift is not settled,
and SmplTrek's QUANTIZE (+0x104) and +0x110 have no clamped counterpart at +0x108 / +0x114 there. The channel defaults suggest channels are stored 0-based with -1 = OFF (CyDrums' PAD CH
default 9 = channel 10; inference).

Cross-flash consequence: a Lofi-12 XT app on SmplTrek flash reads SmplTrek's +0xFC (BATTERY TYPE) as its
ACTIVE SENS word, SmplTrek's AUTO POWER OFF as its BAT.TYPE (values 3-4 fall back to 0), SmplTrek's QUANTIZE as its
AUTO P.OFF, and so on; the 0xFF bytes from +0x11C on fail every clamp and become defaults, except PAD CH (-1 is in
range). All values are range-checked, so the misreads are wrong settings, not wild values,
except in the unclamped words. +0x15C is not unclamped: the validator's last step forces it to 0 unless +0x10 is
negative and +0x15C is not, so on SmplTrek data it becomes 0. Field by field, and which unclamped words anything
reads: next section.

### Lofi-12 XT reading SmplTrek's settings, field by field (2026-11-11)

Static, Lofi-12 XT 1.5.205 only, worked out before device session C3 and checked against it. Input: SmplTrek's PREF
block as it was in the A4 flash dump (device session A4, `experiments/README.md` "A4 flash dump"; flash 0x01FFF000,
both copies identical, captured 2026-11-11 before session D1). The settings on the unit now may differ: 3.0.148 ran
in between, and any settings change since then also changes them.

**How Lofi's `settings_validate` (`0xC2BD31AC`) works, read by hand.**
- It compares the first four bytes with 'PREF'. On a match it copies 404 bytes from the block into `g_settings`
  and will return 0. On a mismatch it copies nothing, keeps `g_settings` as it is in RAM, and will return -1.
- Both paths then store PREX defaults into `g_settings_ext`, and run the same clamp sequence over `g_settings`.
  There are 24 one-field helpers at `0xC2BD2F30`..`0xC2BD3190`: each is "if x < lo or x > hi, store the default".
  The generic one at `0xC2BD308C` takes lo, hi and default in A6 / B6 / B4.
- Three words are forced, whatever was read: +0x60 = 0; +0x108 = 4; +0x15C = 0 unless +0x10 < 0 and +0x15C >= 0.
- Then 404 bytes are copied to the shadow at `0xC2B74B18`, so the next `settings_changed` sees no change and nothing
  is written back until a setting is edited (and with the sterilised patch used in C3, never).
- Every helper's range and default in call order, and the result on SmplTrek's values: scratch script
  `lofi_on_st.py` (not in the repository; the list above and the helper addresses re-derive it).

**Unclamped words** (Lofi copies SmplTrek's value unchanged): +0x10, +0x2C, +0x34, +0x38, +0x3C, +0x40, +0x74, +0x78,
+0x80, +0x84, +0x8C, +0xB0..+0xC8, +0xE4, +0x114. Readers found (address constants, direct and tail calls,

### CyDrums reading SmplTrek's settings (2026-11-12, simulated)

CyDrums 1.1.84's `settings_validate` (`0xC24F6088`) has no clamp helpers: about 2,600 lines of inlined,
scheduled code. Instead of reading it by hand, it was **run** in an execute-packet simulator,
`analysis/c6sim.py`. The simulator has known limits, so it was checked first on results that are known.

**Simulator check** (`analysis/test_c6sim.py`; skips without `firmware/`).
- Lofi-12 XT's `settings_validate` reproduces the hand-read clamp sequence above, used as the oracle, on three
  probe blocks: all words high, all low, all in range. It also reproduces it on a tag mismatch, where RAM is
  clamped and the result is -1. On the A4 block it gives the hand-read result for all 100 words.
- Lofi's `settings_set_defaults` gives the factory defaults that are known: P-COUNT 4, PAD VELOCITY 129, MIDI
  IN/OUT 3/3, channels 13/15/14, TEMPO LED 1, +0x110 = 100, +0x10 = 7 and the pad notes 36, 38, 47, 39, 58, 42,
  46, 49.
- SmplTrek 3.2.174's own `settings_validate` (`0xC159596C`) leaves the A4 block unchanged, word for word. SmplTrek
  wrote that block, so nothing in it should be out of range (independent of any hand reading; needs the A4 dump).
- The hand result agreed with the device in C3 on every row checked.

**How it was run.**
- `python3 -B analysis/c6sim.py settings cydrums firmware/cydrums/CyDrums_v1.1.84.zip --block BLOCK` (or
  `--defaults`).
- One execute packet per cycle, with load and branch delay slots (PROT packets: loads at once), several
  branches in flight, and SPLOOP / SPLOOPD / SPLOOPW with overlapping iterations and SPMASK. The tag compare,
  `memcpy` (`0xC25F8E80`) and the word copy (`0xC26096E0`) run as code. A first scratch version replaced them
  by their effect and gave the same values.
- Inputs:
  - the A4 block from flash 0x01FFF000;
  - erased flash, for the first boot of a relocated build;
  - blocks of +0x7FFFFFF0 and -0x7FFFFFF0, to list the clamped words.
- B14 is `0xC26B0EC0`. `g_settings` (`0xC2426E18`, 376 bytes) starts as zero: it is not in a loaded section,

## Flash use by the app (cross-flash prerequisites)

Every call to `request_read`, `request_erase` and `request_program` in each image, found by target address in
the objdump listing (all are `callp`; no address constant points at these entries, and `do_read` / `do_erase` /
`do_program` are reached only from the driver's task loop). Flash addresses are the app's 32 MiB space
(`flash_select_address`: device 0 below 0x01000000, device 1 above).

| | SmplTrek 3.2.174 | Lofi-12 XT 1.5.205 | CyDrums 1.1.84 |
|---|---|---|---|
| `request_read` call sites | 12 | **5** | 8 |
| Erase / program call sites | 4, all in `settings_save` and its helper | 4, same | 4, same |
| `settings_load`: 4 KiB from 0x01FFF000, else 0x01FFE000 (synchronous) | `0xC159CEB4` | `0xC2C8B214` | `0xC24C5390` |
| Read-back verify in the writer's helper | yes | yes | yes |
| `flash_headers_request` (asynchronous, 128 bytes each) | `0xC159CF70`: 'bmtd' 0x3FFE4 (id 1), 'mmtd' 0x40000 (id 4), 'pmtd' 0x440000 (id 2) | `0xC2C8B2D0`: 0x3FFE4 (id 1), 0x40000 (id 2) | `0xC24C54D8`: 0x3FFE4 (id 1), 0x40000 (id 2) |
| Completion (`FlashDelagate::on_read_done`, vtable slot 1) | `0xC168D8C0` | `0xC2CCE760` | `0xC25EDA00` (also id 8) |
| Other reads | at start-up `preset_pdpt_load` (`0xC161E9A4`): the PDPT partition (flash 0x01000000) into `0xC10E1300`; on FORMAT & DUPLICATE and the other CARD actions, `preset_export_*` read PDSN / PKIT / PISN / PPRJ and write them to the card (see below) | **none** | id 8 from 0x01000000 (device 1, offset 0): 0x40000 bytes into `0xC2068900` (`0xC24C3FA4`, `0xC24C5CCC`) and 0x100000 bytes into `0xC1E68700` (`0xC24C4574`); none of the three functions is referenced anywhere (probably dead code, see below) |

The headers feed the SYSTEM INFO page: `boot_version_string` / `system_version_string` / `preset_version_string`
check the first four bytes against 'bmtd' / 'mmtd' / 'pmtd', then test bit 0 of the word at +12: set gives
"*.*.*", clear gives the three words at +16 / +20 / +24 as "a.b.c" (`version_words_format`; read in all three
products, same code, 2026-11-11). No tag also gives "*.*.*". So the
app sees device 0 as: boot loader region ending with a 'bmtd' header just below 0x40000, the system image
header at 0x40000, and (SmplTrek) the content header at 0x440000, just before the content partitions that
SmplTrek's update files place from 0x441000. In the A4 dump the word at +12 is 0xFFFFFFFE in all three headers;
in the update file's image headers it is 0xFFFFFFFF. Everything else matches the file: the whole 'mmtd' image
in flash equals the one in the A4 build that was installed (`work/a4/dump/SmplTrek.bin`) except byte +12,
and the 'pmtd' header and directory equal 2.0.129's except +12. So the word at +12 is a flag and the version is
the triplet at +16 (an earlier reading took +12 for the version). The boot loader clears bit 0 after it has written
an image (programming can only clear bits; the install marker, `05-bootloader.md` "Writing"), and the app reads a set
bit as "no valid image". Lofi-12 XT has a 'pmtd' buffer and formatter (carried) but never reads that header, and its
SYSTEM INFO page has no PRESET row (seen on the unit in C3).

**SmplTrek's content reads (2026-11-10).** All go through the partition directory in `g_preset_header` (the
128-byte 'pmtd' header at flash 0x440000 that `flash_headers_request` reads at boot): count at +28, then 12-byte entries
{tag, flash address, length}. In the 2.0.129 update file (the last SmplTrek file that carries content) they are PKIT
0x441000, PPRJ 0x451000, PDPT 0x01000000, PDSN 0x01100000, PISN 0x01800000. At start-up `preset_pdpt_load` looks up
'PDPT' and reads it (0x68174 bytes in 2.0.129) into a 512 KiB buffer at `0xC10E1300`. PDPT (read from the 2.0.129 file,
2026-11-10) is the preset drum-pattern library behind the DRUM track's "Loading preset patterns" (manual): an 'AILS'
header (index size, 34 categories, 302 patterns, data offset), 34 'ACTG' category chunks (category name, then pattern
entries of 100 bytes with the pattern name), then 302 'SQPT' pattern chunks with 'SQDK' (the drum-kit file the
pattern selects, a `.stk` name), 'SQPR' and 'SQDT' sub-chunks. Field meanings inside the chunks are not decoded. The
app's readers of the buffer (`0xC161E900` hands it to `0xC166FE60` at start-up; `0xC161F0AC` indexes it) were not read
in detail.
Everything else is the preset export behind SYSTEM MENU > CARD: `preset_export_all` (`0xC159CAB0`, reached from the
FORMAT & DUPLICATE action) calls the exporters for PDSN (/Drum/*.wav), PKIT (.stk kits), PISN (/Inst/*.wav) and PPRJ
(projects), which read their partition and write files to the card; two other card actions export subsets. All of
these only read flash. For foreign content on SmplTrek flash: SmplTrek reads PDPT at every boot, found only through
the directory in the 'pmtd' header; with no 'PDPT' entry the loop ends without a read (`0xC161E9C2` / `0xC161EA40`
branch to `0xC161EAA8` / `0xC161EAB0`), and what the app does without PDPT data was not traced.
Lofi-12 XT reads none of this. CyDrums' unreferenced readers target the same 0x01000000.

**What a cross-flashed Lofi-12 XT app reads from SmplTrek flash:** the two settings sectors and the two
headers, nothing else. From the settings block it copies 404 bytes from block+0 if the tag is 'PREF' (SmplTrek's
284-byte PREF plus 120 bytes of erased flash, 0xFF, see "Settings block"), then clamps the fields.
It ignores the PREX half. CyDrums has code that reads device 1 from offset 0, which on SmplTrek flash is content
data, but nothing reaches it: the three requesters (`flash_dev1_read_a` / `_b` / `_a2` in the CyDrums hand file) have
no caller, no MVK/MVKH constant and no stored pointer (loaded sections and copy-table data searched, 2026-11-10), and
the id-8 completion invalidates only the 1 MiB buffer even for the two 256 KiB requesters. Inference: dead code; a
computed call address is not excluded.

**Settings writer's return value (relevant to the sterilised patch used in C3):** `settings_save` has two entries
in every product: the
direct call from the settings-save path (SmplTrek `0xC154AE60`, Lofi-12 XT `0xC2BAD7B8`, CyDrums `0xC24CE9D4`)
and `settings_reset_and_save` (SmplTrek `0xC159CEA4`, Lofi-12 XT `0xC2C8B204`, CyDrums `0xC24C4564`). The wrapper
calls `settings_set_defaults` and then tail-calls the writer; it is called from next to the SYSTEM RESET /
ALL SYSTEM SETTINGS strings. Neither caller uses the result. After the direct call, the next instruction calls
`tick_count`, which overwrites A4, and the caller only waits until 1000 ticks (1 s) have passed since it started.
After the wrapper, the next callee's first callee loads A4 from memory. The writer itself returns the last flash
status value (WIP clear), which is not a status code. A patch at the writer's entry covers both paths, and
`mvk 0, a4; b b3; nop 5` cannot cause a retry; since no caller uses the result, the explicit `mvk 0, a4` is hygiene,
not a requirement.

**Where the patch has to fit (Lofi-12 XT 1.5.205, read 2026-11-11).** `settings_save` starts at `0xC2C8B0F8`, the
last 4 bytes of the compact fetch packet `0xC2C8B0E0`, whose header word is at `0xC2C8B0FC` (`0xEBC00050`: layout
bits mark word 7 as two 16-bit instructions; expansion bits all 0; p-bits for those two halfwords 0). The entry
is the 16-bit `stw b13` at `0xC2C8B0F8` and `stdw b11:b10` at `0xC2C8B0FA`. **Three 32-bit instructions
(`mvk; b; nop`) do not fit there**: they would overwrite the header and the next packet. What fits is two
16-bit instructions in place of those two, header unchanged:
- `0x0626` = `mvk .L1 0,a4` (the same halfword decodes so at `0xC2B816E2`, under a header with the same, all-zero,
  expansion bits);
- `0xA1EF` = `bnop .S2 b3,5` (the `0x01EF` form, `bnop .S2 b3,0`, already decodes in this same packet at
  `0xC2C8B0EE`; `0xA1EF` is used as `bnop .S2 b3,5` at `0xC2BCD60E`).

With p-bits 0 they run one after the other and return before the stack is touched. Only the two entries
reach this address (the direct call at `0xC2BAD7B8` and `settings_reset_and_save`'s branch at `0xC2C8B20C`);
no address constant or data word points at it. In `Lofi-12 XT.bin` (SHA-256 `a8bffa65…98026`) the entry is at
file offset `0x11FAC4`: bytes `f7 36 77 95` stock, `26 06 ef a1` patched; the header bytes at `0x11FAC8`
(`50 00 c0 eb`) stay as they are. The C3 image was built to this specification on 2026-11-11 by
`tools/patches/sterilise_lofi.py` (output SHA-256 `67d8a6b0…7ea2fb`) and checked by disassembly: only those two
halfwords differ from the stock listing (`experiments/README.md`, "C3 sterilised Lofi-12 XT image"). It ran on the
unit in C3 and left SmplTrek's settings unchanged.

**The same patch fits CyDrums 1.1.84 (read 2026-11-12, specification only).**
- `settings_save` starts at `0xC24C4458`, again the last word of a compact fetch packet (`0xC24C4440`). Its
  header at `0xC24C445C` is the same `0xEBC00050`, and the entry is the same pair: 16-bit `stw b13` and
  `stdw b11:b10`, p-bits 0.
- With the same header, the same two halfwords (`0x0626` `mvk .L1 0,a4`, `0xA1EF` `bnop .S2 b3,5`) decode the
  same way.
- Two entries reach it, as in the other products: the direct call at `0xC24CE9D4` and `settings_reset_and_save`'s
  branch at `0xC24C456C`. No other reference was found in the objdump listing.
- In the extracted `CyDrums.bin` (2,271,021 bytes, SHA-256 `e297d23e…0b6e2155`) the entry is at file offset
  `0xACBF8`. The 8 bytes `f7 36 77 95 50 00 c0 eb` occur only there, and the 24 bytes before them match the ELF
  listing.
- Patched, the entry bytes are `26 06 ef a1`, the header bytes at `0xACBFC` stay, the family word at 0x10 goes
  from 8 to 5, and both CRCs are resealed with the SmplTrek seeds.
- What it reads at boot is in "CyDrums reading SmplTrek's settings" above.
- What it needs on the card is in "CyDrums start-up and the card": with no card it stops at "NO CARD".

Built locally and run on the unit in session C5 (2026-11-20; image SHA-256 `da1b34ac…6399f2f44`; it booted and ran,
results in the session file). `tools/patches/check_sterilised_cydrums.py` checks a locally built image
against this list (read-only; tests in `tools/patches/test_check_sterilised_cydrums.py`, candidates made in memory
only). There is no CyDrums builder.

The writer is the same in structure but not byte-identical across products. Lofi-12 XT's has the same constants and
flash addresses (region_diff: 47 differences, all or/mv encodings, branch offsets and scheduling). CyDrums'
erase-and-verify helper clears and passes a 16384-byte buffer where SmplTrek uses 8192.

**Relocated-settings variant: a cross-flashed Lofi-12 XT that saves its own settings (specification, 2026-11-11;
claim XF-15; session C4, planned only).**
The sterilised image (C3) can't save anything. A "tagged" variant (other tags, same sectors) would
let Lofi save but would erase SmplTrek's settings on its first save. Relocating Lofi's two settings sectors to
unused flash keeps both products' settings.
- **Where.** The top two sectors of flash device 0, `0x00FFE000` and `0x00FFF000`. That area is erased in the A4
  dump and covered by no 'pmtd' directory entry: PPRJ ends at `0x0FC7C18`, and the content updater erases only each
  partition's own range rounded up to 4 KiB. A SYSTEM update erases only `0x40000`-`0x440000`. The boot-area write
  protection covers only the bottom 256 KiB. Nothing in SmplTrek 3.2.174 reads there (its flash reads are the
  settings sectors, the headers and the directory-bounded content).
- **Why device 0.** Lofi builds the addresses with single `set` instructions (`set a4,12,24` = `0x01FFF000`), and
  `+0xC00` (the PREX half) is `set a4,10,24`. Any other spot on device 1 would make `+0xC00` a non-contiguous bit
  range that one `set` can't make. On device 0 every address is the same instruction with the field end 23 instead
  of 24.
- **The complete change:** eight 32-bit instruction words in `settings_save` / `settings_load`. No sterilise stub.
  Each word was checked by decoding it with the tic6x objdump; the p-bits are unchanged, so packet layout and
  headers don't move. These are all the sites: exactly seven `set ..,24` address formations exist in the image, and
  `settings_sector_write_verify` takes its address as an argument.

| Address | File offset in `Lofi-12 XT.bin` (`a8bffa65…98026`) | Old word | New word | Meaning |
|---|---|---|---|---|
| `0xC2C8B144` | `0x11FB10` | `02119888` `set a4,12,24` | `02119788` `set a4,12,23` | erase sector A: `0x1FFF000` → `0xFFF000` |
| `0xC2C8B164` | `0x11FB30` | `02119888` | `02119788` | write A+0 |
| `0xC2C8B16C` | `0x11FB38` | `02115889` `set a4,10,24` | `02115789` `set a4,10,23` | write A+0xC00: `0x1FFFC00` → `0xFFFC00` |
| `0xC2C8B178` | `0x11FB44` | `0211b888` `set a4,13,24` | `0211b788` `set a4,13,23` | erase sector B: `0x1FFE000` → `0xFFE000` |
| `0xC2C8B194` | `0x11FB60` | `0211b889` | `0211b789` | write B+0 |
| `0xC2C8B1A8` | `0x11FB74` | `0200ffe8` `mvkh 0x01FF0000` | `02007fe8` `mvkh 0x00FF0000` | write B+0xC00: `0x1FFEC00` → `0xFFEC00` (low half `0xEC00` unchanged) |
| `0xC2C8B238` | `0x11FC04` | `02119888` | `02119788` | load A |
| `0xC2C8B29C` | `0x11FC68` | `0211b888` | `0211b788` | load B |

Plus the family word (5) and a SmplTrek-seed reseal, as for C3. The diff from the official file would then be
exactly 8 instruction bytes (one per word: `0x98`→`0x97`, `0x58`→`0x57`, `0xb8`→`0xb7`, `0xff`→`0x7f` in the second byte), the family byte and the two CRCs.
- **First boot:** both relocated sectors are erased, so `settings_validate` takes the no-tag path (g_settings
  stays as zero-filled RAM, clamped; PREX defaults). `settings_load`'s result is ignored by its caller
  (`0xC2BACA38`). That is a factory-fresh Lofi state, not an error. The first changed setting is then saved to
  `0xFFF000` / `0xFFE000`, and later boots load it.
- **Effect on SmplTrek:** none. Its settings sectors are never written by this image, so returning to SmplTrek
  finds them as they were (as C3 showed for the sterilised image).
- **Risk to check on the device:** that nothing else on a SmplTrek treats the end of device 0 as its own. The
  static answer is no: the A4 dump shows it erased and unlisted. The device check is a SmplTrek SYSTEM DIAG after
  returning (PRESET still OK), and SmplTrek's settings unchanged.
- **Write review (2026-11-12, `experiments/sessions/C4-relocated-lofi.md`).**
  - `flash_select_address` maps `0x00FFF000` to device 0 at the same offset.
  - `do_erase` issues one 4 KiB `0x20` erase there; its 32 / 64 KiB commands need aligned addresses.
  - The PRESET CRC covers only the `pmtd` header and the five partitions, so DIAG can't see the new sectors:
    recomputed from the dump, it gives the stored `0xCA1D0801`.
  - The only other `mvkh 0x01FF0000` in the image (`0xC2CD9858`) builds a peripheral constant, `0x01FF1E1F`.
  - Lofi saves on a normal power-off (`MainDelegate::handle_power_message`, call at `0xC2BAD7B8`) and on SYSTEM
    MENU > RESET (`0xC2CACD60` → `settings_reset_and_save`).
- **Checker:** `tools/patches/check_relocated_lofi.py` checks a locally built image against this table (read-only;
  tests in `tools/patches/test_check_relocated_lofi.py`).
- **Status:** specification only; no image of it has been built or run.

## CyDrums start-up and the card (static, 2026-11-12)

CyDrums keeps its sounds on the card (`/CyDrums/System/SystemCore.bin`, configs and projects under `/CyDrums`).
This section answers what a cross-flashed CyDrums app does with no card or with a SmplTrek card. Read by hand from
CyDrums 1.1.84 execute packets, with the card writes simulated where marked; no CyDrums image has run on the unit.

- **Start-up sequence** (MainDelegate set-up, `0xC24CDF54` onwards):
  1. `settings_apply_all` (`0xC24EE074`). Where the settings load happens before it was not re-read here.
  2. `sd_card_inserted` (`0xC25C226C`).
  3. If a card is there, the mount wrapper (`0xC2565A70`: `f_mount`, two buffer clears, no `f_mkdir`).
  4. If it mounted, `file_exists("/CyDrums/System/SystemCore.bin")` (`0xC2565A50`).
  5. If the file exists, it loads `.SoundConfig`, `.EfxConfig`, `.KitConfig` and `Project.lst`, then starts the
     ResourceLoader task.
  6. If the file is missing, it posts a message with code 14.
  7. In every case, it then asks `0xC2566374` (card mounted?) and selects the first page: AppNoCard (instance
     `0xC242FFD8`: `mvk -40` sign-extends before `mvkh 0xC2420000` at `0xC24CDCB0`; first misread as `0xC241FFD8`)
     if not, another page if so (recorded as `0xC241F168`, not identified and not re-checked: it may carry the same
     sign-extension misreading).
- **Code 14 → AppNoSystemCore.** The MainDelegate message switch (`0xC24CE6C8`-`0xC24CE6E0`) sends code 14 to
  the page change with AppNoSystemCore (instance `0xC242FFE8`, 2026-11-18: `mvk -24` sign-extends before
  `mvkh 0xC2420000`, and after boot the vtable `0xC269BB60` is there; first misread as `0xC241FFE8`). Its screen is "BLANK MEDIA! / DOWNLOAD FILES /
  FROM THE WEB. / https://sonicware.jp" (strings `0xC269C908`-`0xC269C932`), the manual's start-up error page
  (p. 167). Its update method checks `sd_card_reader_active` (`0xC25C23C0`), which fits the manual telling the
  user to connect USB and copy the CyDrums folder.
- **No card → AppNoCard** ("NO CARD", "INSERT CARD!"). The card-state lambda (`0xC25D0140`) does the same at run
  time: on removal, if not mounted, it switches to AppNoCard; on insertion, it mounts and repeats the
  SystemCore.bin check (`0xC25D0204` onwards).
- **Both pages swallow input.** Vtable slots 4, 6, 7 and 8 (buttons, encoders, pads; slot numbers as in Lofi,
  inference) are `return 1` in both classes (`0xC25ECC34`-`0xC25ECC46`, `0xC25D6F10`-`0xC25D6F22`). Whether
  MainDelegate's global func + key handling still reaches SYSTEM MENU over them was not traced.
- **Card writes, simulated (2026-11-12): none on these paths.** `analysis/cydrums_card_check.py` builds
  CyDrums' start-up state in `c6sim.py`: copy table, the 13 SYS/BIOS module start-up functions, then the 181
  `.init_array` constructors. It runs the paths a foreign card reaches with FatFs and the disk layer hooked: a card
  that is present and mounts, where every lookup fails and every write-side call is logged and refused. The paths
  are the start-up card block (entered at `0xC24CDFA4`), the card-insertion lambda with event "inserted", and
  AppNoSystemCore's enter and update methods. Result: `f_mount` and one `f_stat("/CyDrums/System/SystemCore.bin")` on
  the first two, nothing on the page, and **no** `f_mkdir`, write-mode `f_open`, `f_write`, `f_rename`, `f_mkfs`,
  `f_sync`, unlink or `disk_write`. Controls: through the app's own wrappers, `file_mkdir` and `file_open` in write
  mode are caught and refused by the same hooks. Tests: `test_cydrums_card_check.py`.
  - **Replaced by stubs:** hardware polls (PSC1, codec I2C busy flags, USB0 reset and PHY clock), the flash
    requests behind `settings_load` / `flash_headers_request`, `task_sleep`, and `Memory_alloc` / `Memory_free` (a
    bump allocator: the simulated SYS/BIOS heap returned NULL, which would have hidden write paths that allocate
    first). The nested-SPLOOPD table initialiser `0xC253FA24` is not stubbed and not reached on any of these paths
    (output identical with and without a stub; callers `0xC246EBF8` and `0xC253FE44` not traced); c6sim models nested
    reload and runs it (claim TOOL-3).
  - **Not covered:** other SYS/BIOS tasks (the ResourceLoader only starts when SystemCore.bin exists; the
    AudioFileControlTask only works on request), user actions (project, sample or pattern saves, CARD menu), and USB
    card-reader mode, where the computer writes the card. The folder-creating code (`f_mkdir` wrapper `0xC2565AD0`,
    eight call sites) is still reachable from those.
  - **What follows for a device run (inference; adopted in the C5 plan):** with a spare card, boot CyDrums, look at
    the "BLANK MEDIA!" page, and power off without pressing anything, USB unplugged. The SmplTrek card stays out.
- **Settings.** The settings path is the same as Lofi's (load and clamp at start-up, save on power-off and on
  RESET; `settings_save` entries in "Flash use by the app"). So a CyDrums run on a SmplTrek needs the sterilised
  (C3-style) or relocated-settings patch, whatever the card does.
- **What a device run could show.** With the card out, CyDrums should boot to "NO CARD / INSERT CARD!". That is a
  useful boot and display test with no card writes, but little else is testable. A functional test needs a
  separate card prepared from `CyDrums_folder.zip`, which CyDrums will write to (configs, projects, `filedb.bin`).

## CyDrums wavetable bank (SystemCore.bin; 2026-11-24)

CyDrums' 64 oscillator wavetables (WAVE 1-64) are on the card, in `/CyDrums/System/SystemCore.bin` from
`CyDrums_folder.zip` (67,116,544 bytes). Decoded from that file and CyDrums 1.1.84 code; the tool
`tools/cydrums_wavetables.py` lists, exports and rebuilds it (tests: `tools/test_cydrums_wavetables.py`, with a
byte-for-byte rebuild of the stock file when the zip is present; user guide `18-cydrums-wavetables-howto.md`).

- **Chunk shape:** `tag[4]`, u32 total length (header included), three u32 header words, payload. The same
  container as `.SoundConfig` (DNPP / PTC0), `.KitConfig` (DNKP), `.EfxConfig` (DNEP) and the project files (DNP0).
- **Index:** `WTLS` (words 0, 64, payload length; 7400 bytes) holding 64 `WTDT` records (0, 3, 0), each with
  - `WTNM` (0, 1, n): the display name, NUL-terminated, 0xFF-padded to a multiple of 4 (8 or 12 bytes in the stock
    file). The firmware has no copy of these short names, so the screen shows WTNM.
  - `WTFT` (0, 1, 16): u16 0, u16 channels (1), u32 rate, u32 0, u16 0, u16 bits (16). Rate: 24000 for 50 tables,
    11 at 44100, 384000 for SmpSnare / SmpCymbl / SmpCrsh.
  - `WTPL` (0, 1, 8): u32 offset (slot x 0x100000), u32 length (0x100000).
- **Data:** from base = (WTLS length + 511) & ~511 = 0x1E00 (index reader `0xC25ABBF0`, rounding at `0xC25ABCC8`;
  0xFF fill before it). Each table is 1 MiB of signed 16-bit little-endian mono: 256 frames of 2048 samples
  (autocorrelation peaks at 2048 in every periodic table; the three Smp tables are plain samples).
- **Reader:** `0xC25ABBF0` opens the file, reads the 8-byte header, then the whole index; `0xC25ABB4C` walks the
  WTDT records and `0xC25ABA08` their children into a 64-entry table (24 bytes each: WTFT then WTPL; names kept
  separately; count at +1544). At most 64 entries.
- **Loader (`0xC25AB8D0`):** on demand, when a sound uses the table: allocates 1 MiB, `file_lseek` to base + offset,
  reads `length` bytes, keeps channels, rate and bits, sample count = length / (bits / 8 x channels). In the
  emulator, the tables the shipped project's sounds use are loaded at start-up (about 9,900 SD read commands in
  6 s); the others are not.
- **Patches refer to wavetables two ways:** `PWT0` (one per oscillator, header word 1 = oscillator) starts with a u16
  wavetable number, 0-based, 0xFFFF = none; `PWP0` holds the stock source file name (`sine_moph1_24k_16.wav`), from
  a fixed 64-pointer table in the firmware (`0xC26C4950`, same order as the bank). All 64 numbers are used by the
  shipped projects. Which of the two the firmware trusts on load is not traced, so a custom bank should keep slot
  order: replacing slot N changes every sound that uses WAVE N.
- **Custom bank, checked in the emulator (2026-11-24, `emulator/tests/stock_cydrums_wavetables.py`):** with the
  shipped bank, CyDrums 1.1.84 loads 24 tables at start-up (slots 1, 3-21, 43, 45, 62, 63), each equal to the file.
  With a bank built by the tool (slot 1 a 4-frame saw-to-square morph; all 11 short-named slots renamed to 10
  characters, so the index grows to 7444 bytes and later records move) it loads the same 24 slots, slot 1 with the
  new data and no stock slot 1 anywhere in RAM, and the rest equal to the card. Not run on a unit; the sound and
  the displayed names were not checked.
- **Not known:** where the engine uses the rate word (the tool writes 24000), and how the oscillator maps WAVE
  position onto the 256 frames.

## CyDrums 2.0.97 beta (2026-11-18)

The beta update `CyDrums_v2.0.97beta.zip` (same container, one system image, no content or MCU images) adds sampling
and sample slots. Function match against 1.1.84 (`func_match.py`): 8985 of 9849 functions found, 10337 in 2.0; the

- **Container:** the CyDrums seeds fitted to 1.1.84 verify it unchanged (INT-4), so `sonicware_integrity.py` has a

  `0xC25527F8`; the C3 sterilising patch would go there, but `check_sterilised_cydrums.py` pins 1.1.84).
- **New classes (RTTI, 19, none removed):** AppSampling, AppSamplingRename, AppImportSampleSound,
  AppSampleSoundBrowser, AppSampleSoundRename, DialogSampleOverwrite, `AudioVisualizer<512>`,

  empty, 1 to load, 3 loaded; then the path), and the audio at `0xC3800000 + (slot << 18)` (256 KiB each), lengths at
  `0xC2488A48`, clamped to 0..128000 (`0xC265CA6C`). Slot functions: `valid_slot` `0xC2611220`, `valid_name`

  `assign_slot` `0xC2611714`, `clear_slot` `0xC2611314`, reset `0xC2611284`.
- **`/CyDrums/Contents/Samples/SlotInfo.lst` (read from code):** ASCII text, no header: exactly 32 lines ending
  CRLF, line N = slot N's full path or empty (64 bytes when all slots are empty).
  - Writer `0xC2612810`: creates the Samples folder if missing (`f_mkdir` wrapper `0xC25E2E50`), opens the list
    for writing (`0xC25E2EEC`), writes each slot (empty line when the state byte is 0), closes; 0 or -1.
  - Reader `0xC2612A94`: 512-byte reads, splits on LF and drops CR, first 32 lines; a line is kept (state 3) only
    if it is 1-255 characters, starts with `/`, is printable ASCII and is not already in another slot.

    `clear_slot` (browser delete `0xC25FA4D4`, which empties the slot and deletes no file that was seen).
- **Sample files (read from code):** `/CyDrums/Contents/Samples/<name>.wav`, a plain `AudioEngine::WavFile` (no

  - **Import does not copy:** AppImportSampleSound assigns the chosen file's own path to the slot, so the list can
    point anywhere on the card. Source formats read by the loader (inference): PCM 8/16/24/32-bit and 32-bit float.
  - **Inputs:** MIC, HIZ, DYN, LINE, USB; gain NORMAL / HIGH / LOW; PAD; L+R; AUTO REC (strings). The auto-rec
    threshold was not found.
- **Card writes, simulated for 2.0.97 (`cydrums_card_check.py`, which now picks the version from the image):**
  - Foreign card (every lookup fails): the same as 1.1.84. The start-up card block (`0xC253F4B0`; it now also runs

    `f_mount` and `f_stat("/CyDrums/System/SystemCore.bin")`; AppNoSystemCore (`0xC249B2DC`) makes no card calls.
    Run from the top of the start-up routine (`0xC253F320`, scratch only): the same two calls.
  - Real but old card (`--system-core`: only the SystemCore.bin `f_stat` succeeds), identical in 1.1.84 and 2.0.97:
    `f_open` in mode 0x6 (create new, inference from the FatFs flag values) of `.SoundConfig`, `.EfxConfig` and
    `.KitConfig`, and `f_mkdir("/CyDrums/System/Project/Project001")`: 4 write-side calls per path, all refused by
    the hooks, so later behaviour on a real card may differ. SlotInfo.lst is not opened on these paths. A card
    with SystemCore.bin but no configs gets them created at start-up, in both versions.
  - Not covered: the ResourceLoader task (it reads SlotInfo.lst and writes nothing when the file is missing,
    simulated alone), user actions (sampling, import, rename, delete), USB card-reader mode.

## SPI flash layout (SmplTrek only; read from the A4 dump, 2026-11-11)

The A4 dump (`work/a4/A4DUMP.BIN`, 32 MiB, SHA-256 `3767d6ad…e4c8d5`, not committed; how it was taken:
`experiments/README.md`, "A4 flash dump") is accounted for byte by byte with `analysis/flash_map.py`, which
takes the regions from the headers in the dump and compares every partition with the official update files.
Only SmplTrek has been dumped; Lofi-12 XT and CyDrums layouts are not known beyond what their apps read (see
"Flash use by the app"). Addresses are the app's 32 MiB space (device 0 below 0x01000000, device 1 above).

| Range | Contents | Checked against |
|---|---|---|
| 0x0000000..0x0036B3C | Boot loader 1.0.17: TI AIS image ('TIPA' magic), 224,060 bytes | extracted and traced in `05-bootloader.md` |
| 0x0036B3C..0x003FFE4 | erased | |
| 0x003FFE4..0x0040000 | 'bmtd' header, 28 bytes: size 0x40000 (the whole boot region), CRC word, +12 0xFFFFFFFE, version 1.0.17 | no file carries it |
| 0x0040000..0x021DF6D | 'mmtd' system image (here the A4 build of 3.2.174), then erased to 0x440000 | equals the installed build except +12 |
| 0x0440000..0x044005C | 'pmtd' header and 5-entry directory, PRESET 2.0.22; rest of the sector erased | equals 2.0.129 except +12 |
| 0x0441000..0x0450BDC | PKIT | equals 2.0.129 |
| 0x0451000..0x0FC7C18 | PPRJ, then erased to the end of device 0 | equals every release (1.0.65 to 2.0.129) |
| 0x1000000..0x1068174 | PDPT, then erased to 0x1069000 | equals 2.0.129 |
| 0x1069000..0x1100000 | **stale**: no directory entry covers it | equals the 1.x PDSN at the same addresses (1.0.65 to 1.4.99 placed PDSN at 0x1000000) |
| 0x1100000..0x1748EB8 | PDSN, then erased to 0x1800000 | equals 2.0.129 |
| 0x1800000..0x1F7E52E | PISN, then erased to 0x1FFE000 | equals every release |
| 0x1FFE000, 0x1FFF000 | settings sectors: 'PREF' at +0, 'PREX' at +0xC00, 0xD74 bytes used, the rest erased | both sectors identical in this dump |

What the layout shows:
- **Every non-erased byte belongs to one of the rows above.** In particular there is **no MCU image** in the SPI
  flash: no region is left for it, and no plain Cortex-M vector table (stack pointer in 0x20000000..0x20010000
  followed by Thumb vectors in 0x08000000..0x08010000) occurs anywhere in the 32 MiB, boot data included (a
  compressed or encrypted copy inside the boot data is not excluded). So SYSTEM DIAG's "MCU v1.0.6" is not a fourth
  image in this flash (claim INT-10; an earlier reading assumed it was). The boot data does carry MCU handling: the
  class name `RomHandlerMCU`, `SystemUpdater::updateMCUSection` and `updateMCUBootSection`, and the menu strings
  ">> MCU" and ">> MCU Boot". In BOOT 1.0.17, DIAG's MCU check sends `0x93` on the panel UART and waits for reply 12,
  and the bootloader cannot read the MCU's flash back (INT-10, `05-bootloader.md` "Panel MCU programming").
  Inference: the panel MCU keeps its firmware in its own flash, and an update file could carry MCU sections under
  descriptor types not seen so far.
- **The content updater erases per partition in 4 KiB steps.** The 2.0.129 content install (the unit shipped
  with PRESET 1.0.11, `experiments/README.md` run 1) erased PDPT's range up to 0x1069000, which is
  PDPT's length rounded up to 4 KiB. It left the old PDSN bytes from there to 0x1100000, where the new PDSN
  starts. So the boot loader erased neither the whole device nor whole 64 KiB blocks there.
- The slots have room to spare: the system slot is 4 MiB (0x40000..0x440000, 3.2.174 uses 1.87 MiB). Device 0
  ends 0x383E8 bytes after PPRJ, and device 1 has 0x7FAD2 bytes between PISN's end and the settings sectors.
  The PRESET 1.0.11 content of every 1.x release is the same layout with PDSN at 0x1000000 and no PDPT.

## Other buses: is there any memory besides the SPI flash? (SmplTrek only, 2026-11-11)

Static census of every C6748 peripheral address the SmplTrek 3.2.174 app and the 1.0.17 boot loader build with
MVK/MVKH, then the I2C and SPI drivers read by hand. Lofi-12 XT and CyDrums were not checked here.

| Bus | What is on it | Evidence |
|---|---|---|
| I2C0 | one slave, **0x18** (the AIC310x codec) | The only ICSAR (+0x1C) writer is `0xC167BE48`. It is reached from the transfer function `0xC160C78C`, whose only caller is the thunk `0xC1671E90` (slave 24, from `0xC162158C` before `codec_i2c_init`). The other route to it (`0xC160CC28`) has no caller and no stored pointer. The I2C open (`0xC160CE04`) has one caller, with instance 0 |
| I2C1 | nothing | The base appears only in the instance-to-base lookup (`0xC168EC88`), the PSC enable for instance 1 and the EDMA-event choice (`0xC160C814`), all generic driver code; the open is never called with instance 1 |
| EMIFA (parallel flash / NAND / SDRAM) | nothing | No MVK/MVKH constant in the app or the boot loader points at the EMIFA registers (0x68000000) or its chip-select windows. The two image words that look like it are data (after an RTTI string; inside packed table bytes). The AIS image calls only ROM functions 6 (PLL and clock) and 3 (mDDR/DDR2 controller); 4 and 5, the EMIFA set-ups, are not called (function numbers per TI SPRAAT2) |
| SPI0 | the two 16 MiB flash devices | `g_spi_driver` (`0xC1504390`): SPIDriver open with instance 0, pin mask 0xE03 (SCS0, SCS1, CLK, SIMO, SOMI), 32 MHz; `select` (`0xC1626888`) drives chip-select 1 << device, so device 0 = SCS0 and device 1 = SCS1 |
| SPI1 | the display, and a dormant output engine | `0xC15043B0`: instance 1, SPIPC0 0xE01 (SOMI, SIMO, CLK and SCS0 as SPI pins, SPRUH79C Table 28-14), 9 MHz; the OLED's command/data traffic (inference from its init code). `0xC15043A0` (`g_spi1_driver_gpio_cs`): instance 1, SPIPC0 0xE00 (SOMI, SIMO, CLK; no hardware chip select), 1453125 Hz, used by a **frame engine** (`frame_engine_init` `0xC15FC880`): a 198-byte buffer in L1D (3 groups x 11 frames x 6 bytes), linked EDMA sets that timer 0 (TIM34 event, EDMA channel 11) steps through, sending each frame on SPI1 (transmit channel 19 only, nothing received) with GPIO set/clear writes between frames, three GPIO lines GP7[11..13] and an enable line GP2[15]. `frame_set_level` gives each output a 10-step on-time (PWM brightness). **It is never started**: `frame_engine_start` / `_stop` / `frame_set_level` have no call, branch or stored pointer (copy-table data included) in 3.2.174 or 1.0.65; only the init runs at start-up, and it leaves the enable line low. The same code is in Lofi-12 XT and CyDrums (func_match 1.0), also without callers of the start function |

So the boot loader and the app reach no I2C memory, no parallel memory and no SPI device other than the flash
that holds data. The only storage they address is the SPI flash and the SD card. Two things are left open:
- **What the SPI1 frame engine was built for.** It only sends and is never started, so it is not memory and
  reads nothing; its shape (3 x 48 outputs, 10-step PWM) fits a directly driven LED or display matrix, perhaps
  from an earlier board, but no part number or user exists in the code (inference). The panel LEDs are driven
  by the panel MCU instead: `led_set` caches each value in `g_led_state` (144 bytes) and sends
  `{0xC1, a, b, c, value}` over the panel UART (`panel_led_command`), which is the path the AppTestLED page and
  ClippingLED use.
- **The panel MCU's own flash** (see "SPI flash layout").

Also readable, but holding no unit-specific data: DDR, L2 and shared RAM (runtime state), the TI boot ROM, and the
chip ID / boot-configuration registers.

`MIDIInputPort::handle_channel_message` is identical in SmplTrek and Lofi-12 XT (region_diff, 0 differences).
CyDrums' copy was read in Ghidra's listing (`ghidra_import.sh` run for CyDrums; objdump shows the same
instructions there with spurious `|| nop 5` tails), with the delay slots followed packet by packet. So the slot
numbers are per product: everything from pitch bend on is one slot higher in CyDrums. CyDrums' slot 4 is channel
pressure: its dispatcher issues a second branch (`[b0] b 0xC25A7EB0`, b0 = status == 0xD0) inside the delay slots of
the branch at `0xC25A7D64`, which a first reading missed; packets.py shows both. SmplTrek's dispatcher has no 0xD0
compare. CyDrums' handler routes the
pressure to every track whose channel (the 8-word array at g_settings+0x90) matches, then to the AUTO channel. The handler bodies are product code (none func-matched); per-product addresses are in the hand files.

## Display (verified identical driver)

`OLEDDriver` (a `Graphics::DisplayDriver`, 7 virtuals) is the same code in all three products: region_diff
over the whole class shows 140 vs 140 instructions with only moved data addresses and data-page offsets, and
the command/data helpers before it match the same way.

| | SmplTrek 3.2.174 | Lofi-12 XT 1.5.205 | CyDrums 1.1.84 |
|---|---|---|---|
| `g_oled_framebuffer` (8 KiB) | `0xC14B8400` (the code builds `0xC14B0000` + `0x8400`; once mistyped `0xC1498400`) | `0xC2B2D700` | `0xC23D6880` |
| `g_oled_framebuffer_saved` (8 KiB) | `0xC14BA400` (once mistyped `0xC149A400`) | `0xC2B2F700` | `0xC23D8880` |
| `OLEDDriver::flush` (slot 2) | `0xC1672400` | `0xC2CA8D40` | `0xC25C2140` |
| `OLEDDriver::framebuffer` (slot 5) | `0xC1672484` | `0xC2CA8DC4` | `0xC25C21C4` |

- **Geometry: 128 x 128, 4 bits per pixel** (two pixels per byte, 16 grey levels). The size is the 8192-byte
  clear/flush length; the shape comes from `draw_text_impl`, which in all three clips x and y against 128 and
  indexes the buffer as `128 * (y >> 1) + 64 * (x & 1) + (x >> 1)`, the even row of each pair in the low nibble and
  the odd row in the high nibble: row pairs in 128-byte blocks, even columns then odd columns (claim HW-35, seen on
  the unit; an earlier static reading, `((y << 7) + x) >> 1` with even x in the low nibble, was wrong). Bus,
  pins, register sequence and the full layout: `docs/04-hardware-access.md`, "Pixel format".
- **Panel controller**: init sends `B3 F0`, `81 FF`, `A0 07`, `AF` with the data/command GPIO low; frames go
  with it high. These opcodes fit an SSD1327-family 128x128 grey OLED controller (inference; no part number seen).
- **Flush**: `OLEDDriver::flush` waits until at least 33 ticks have passed since the previous frame
  (`oled_frame_wait`), writes the framebuffer back from the cache (`Cache_wb`, 8192) and sends it over SPI.
  So anything drawn into `g_oled_framebuffer` reaches the panel only after a cache write-back, which the app's
  flush does. One tick is 1 ms (section "Clock tick"), so at most about 30 frames per second.
- Slot 3 copies the framebuffer into `g_oled_framebuffer_saved`, slot 4 clears that copy, slot 6 returns it;
  the panel only ever receives `g_oled_framebuffer`.

## Clock tick (1 ms in all three)

`tick_count()` returns the SYS/BIOS Clock tick count `g_clock_ticks`, incremented by `clock_tick` (same code in
all three, region_diff). The timer object that calls `clock_tick` holds period 1000 with periodType 0
(microseconds) and interrupt 14 in all three products (initialised data, decoded from the copy table). So one
tick is 1 ms (probable; the field layout is read against SYS/BIOS's timer object). This gives real times
for the OLED frame pacing (33 ms), the encoder acceleration buckets (2 ms) and the app's 1000-tick timeouts (1 s).

| | SmplTrek 3.2.174 | Lofi-12 XT 1.5.205 | CyDrums 1.1.84 |
|---|---|---|---|
| `tick_count` | `0xC16ACDA0` | `0xC2CEC340` | `0xC2617CC0` |
| `g_clock_ticks` | `0xC16F3EE4` | `0xC2DA7168` | `0xC26B1938` |
| `clock_tick` | `0xC169C340` | `0xC2CD8FC0` | `0xC25FF6C0` |
| `g_clock_timer_period` (= 1000) | `0xC16ECF18` | `0xC2D80A20` | `0xC2681198` |

## Tasks (static SYS/BIOS tasks, priorities per product)

All tasks are static SYS/BIOS Task objects in initialised data (copy table, decoded with `memory_map.build_map`); no
`Task_create` call was found. Each object is 92 bytes: priority at +8, mode at +20, stackSize at +28, stack at +32,
fxn at +40 (layout read against SYS/BIOS `Task_Object`, probable). Every TaskHandler task has the same fxn
(`task_handler_entry`), mode 4 (inactive) and priority -1, except the main task, which is static at priority 3.
The stacks are one static block in DDR. The app starts each task in two steps:
`task_handler_bind(th, handle)` stores the handler in the task (the handle comes from a B14 global), then
`task_handler_set(th, priority)` sets the priority, which makes the task runnable. `task_handler_entry` then
calls the handler's vtable slot 0 (its run loop). The Idle task (priority 0, its own fxn) ends the table.

Each value was read at the call that sets it, with the execute packets decoded from the fetch-packet p-bits.
Lofi-12 XT and CyDrums use the same platform order: the platform tasks are one level below SmplTrek's, and their
pattern sequencer task gets the top priority (15). SmplTrek builds the constants into the callees. In Lofi-12 XT
and CyDrums most start functions take the priority as an argument (A4, or B4 forwarded) and the caller passes it,
usually in the same execute packet as the call. Addresses of every start function and handler object are in the
symbol files (`*_start`, `*_set_priority`, `g_*_task*`, `g_io_observer`).

`graphics_task_stop` (SmplTrek `0xC162A108`) posts event 32 to the graphics event object and waits until
`task_handler_get_mode` returns 3 (terminated). It is part of the power-off sequence: settings save at `0xC154AE60`,
the 1-second wait, `graphics_task_stop`, then `power_hold_release` (see "Power management").

Reading notes: each value is a single call (a SmplTrek "15/3" once recorded here was one call with 15; the 3
belongs to the next function). The panel task priority in Lofi-12 XT and CyDrums is 12, set by their caller (see "Hardware
layer").

### Audio file commands (AudioFileControlTask; read in each product 2026-11-10)

The audio engine does its card I/O in this task (priority 1). Callers use the `AudioFileControlTask::post_*` request
functions (all three symbol files), which build a five-word message {cmd, stream, m2, m3, m4} and post it with
timeout 0; requests with a wait flag then Event_pend on `g_audio_file_control_event`. The task posts 1 for success, or
for a nonzero result of `file_exists` / `file_mkdir` / `file_unlink`, and -1 otherwise. So `post_exists` returns 1 when the
file exists, and `post_unlink` / `post_mkdir` return 1 when the FatFs call failed. A stream is a double-buffered
file object: 8 zeroed bytes, an `AudioEngine::ExpandedWavFile` at +8 (RTTI; base `AudioEngine::WavFile`: `open/seek/tell/flush/close`,
virtual slot 0 `write`, slot 1 `read`) and a listener (slot 0 read done, 1 block written, 2 opened). SmplTrek's writer posts a 64 KiB buffer (`post_write`) each time one fills.

| Command | SmplTrek 3.2.174 | Lofi-12 XT 1.5.205, CyDrums 1.1.84 | Request function |
|---|---|---|---|
| write block (m4 buffer, m3 length; then listener slot 1) | 0 | 0 | `post_write` |
| read at m2 (seek only if `AudioEngine::WavFile::tell` differs); 1 silent, 2 notifies listener slot 0, 3 synchronous | 1-3 | 1-3 | `post_read` (mode 1 -> 3, 2 -> 2, else 1) |
| seek | 4 | 4 | `post_seek` |
| open (m4 path, m2 mode) | 5: wait flag, or result to listener slot 2 | 5: always synchronous, returns 0 / -1 | `post_open` |
| (nothing) | 6 | — | none |
| write last buffer, close | 7 | 6 | `post_write_close` |
| close, free the stream | 8 (72-byte object) | 7 (608 / 576 bytes, plus one extra call) | `post_close_free` |
| write last buffer, flush | 9 | 8 | `post_flush` |
| exists / mkdir / unlink (m4 path, synchronous) | 10 / 11 / 12 | 9 / 10 / 11 | `post_exists` / `post_mkdir` / `post_unlink` |

After every write block, SmplTrek and Lofi-12 XT run `card_space_check(0)`, which returns 0 when less than 128 MiB
(0x08000000 bytes) of the card is free (`card_free_space`: f_getfree clusters x sectors per cluster x 512). Lofi-12 XT then
posts app message {5, 2, -2, 0}. SmplTrek posts {5, 2, -1, 0} when `g_app_state_676` (B14+676) is 4, nothing when it is 2,
else {5, 2, -2, 0}; `MainDelegate::handle_app_message_5` handles sub-code 2 with -1 / -2 on two UI paths.
What they do (2026-11-14, static):
- State 4 is "recording a global track to the card". `0xC15E9C6C`, called from `AppGlobalTrackEdit`'s enter method,
  checks card space, makes the folder if needed, opens two audio file streams, then sets 4. `0xC15E9C18` is its stop
  and sets 0.
- On low space in state 4 (-1), `0xC15EA0F4` stops that recording through `0xC15E9C18`, then opens
  `DialogCombineRecordedAudio` (the static dialog `0xC1503890`, class from its vtable after start-up) through
  `0xC1659240`.
- In other states (-2), `0xC1548C20` stops and closes the active `AudioEngine::AudioFileStream` (`0xC1500E48`, through
  `0xC1625C90`) and calls `graphics_set_continuous`; it opens no dialog.
- State 2 posts nothing. It is quick sampling: set by `HomeModeController::on_pad_hold_long`, the long, hard press
  on a track pad that SmplTrek 2.0.129 added ("Quick sampling: by putting pressure on the track pad, you can easily
  record a sample", Sonicware's 2.0.129 release notes). The hard-press tracker is
  `pad_hold_update` (hard above 2800).
- Constants stored by `app_state_set`: 0 (the track edit pages' enter methods, MainDelegate, the loop track view, the
  recording stop), 1 (helpers next to the Inst / Drum / Audio track edit pages), 2, 4. Most other sites store a
  register value.
- No string is referenced on these paths; the dialog draws its own text.

CyDrums' write command has no such check. The listener sits at stream +60 / +592 / +560 (SmplTrek / Lofi-12 XT /
CyDrums). Older images number differently: SmplTrek 1.2-1.4 use 3 seek, 4 open, 5 write and close, 6 close and free,
7 flush, 8 / 9 / 10 exists / mkdir / unlink, with read modes 1-2 only (1.0 / 1.1: 8 exists, 10 unlink, and 9 calls a
thunk to f_mount, not read); 2.0.129 and 3.0.148 use 9 / 10 / 11 for the path commands. The path requests differ
only in the constant, so automatic carrying swapped them; hand files name them in every image (SmplTrek
1.0.65-3.0.148, Lofi-12 XT 1.1.156 / 1.5.205, CyDrums).

### WAV files written and read by the streams (read in each product 2026-11-11)

FatFs here keeps `buf[512]` at the start of FIL (inference from the offsets): `f_read` validates the object at +512 and uses objsize at +524 and fptr at +536,
and the FIL is 556 bytes. So `file_tell` / `file_size` read +536 / +524 (identical in all three). `AudioEngine::WavFile` keeps the
FIL* at +4, the 16-byte PCM format block at +8, the data start at +24, the data byte count at +28 and the open mode at +36.
`tell` and `seek` positions are relative to the data start.

- **Open to create** (open-mode flag words at B14+1512..1524, values set at run time): write_riff_header(size 0), write_fmt_chunk at 12,
  vtable slot 2 (extra chunks), write_data_header(size 0) at the end, data start = file size.
- **Open to read**: `read_chunks` checks RIFF/WAVE, then walks the chunks.
  - "fmt " is copied to +8 and must have format tag 1 (PCM).
  - "data" sets +24 / +28.
  - Every other chunk goes to vtable slot 3.
  - Open then seeks to the data start.
- **flush**: rewrites the RIFF size and the data header only.

| | SmplTrek 3.2.174 | Lofi-12 XT 1.5.205 | CyDrums 1.1.84 |
|---|---|---|---|
| WavFile helpers (riff / data / fmt / read_riff_header / read_chunks) | `0xC161680C` `0xC1616884` `0xC1616E6C` `0xC1616AA0` `0xC1616BAC` | `0xC2C50C6C` `0xC2C50CE4` `0xC2C512EC` `0xC2C50F20` `0xC2C5102C` | `0xC256A6CC` `0xC256A744` `0xC256AD4C` `0xC256A980` `0xC256AA8C` |

- **Tempo word:** the project tempo is a word holding tempo x 10, default 1200 (inference from the default and the label format).
  - SmplTrek keeps it at `0xC1500CF4` (`project_get/set_tempo_x10`); Lofi-12 XT at `0xC2B72094`; CyDrums at `0xC2683428` (`0xC256F000` / `0xC256F010`, same 100 / 1200 initial pair).
  - In SmplTrek, the files created after those two `set_tempo` calls are labelled with the project tempo. Lofi-12 XT and CyDrums write the label from +48, which the constructor zeroes; no write of the project tempo there was found.
- **smpl writer:** each image also contains a "smpl" writer (one loop, unity note 60), but no call to it was found in any of the three.
- **ORSL and AFTG in Lofi-12 XT** (2026-11-11):
  - **AFTG holds a sample's tags** (probable). `audio_files_save_tags` (`0xC2BBF5B4`; its caller loads "SAVING TAGS") rewrites each changed file with a new 8-byte value. The manual: 15 tags plus Favorite, "Tag information is stored in the audio file".
  - **ORSL is the slice list** (inference). `audio_file_save_slices` (`0xC2C76728`) rewrites a file with new records and keeps its AFTG. This matches the manual's "Saving slice data" (written to the audio file).
  - **Record limit:** 15 in 1.1.156 and 16 in 1.5.205, which matches the 1.5 release note "Expand up to 16 slices".
  - **Rewrite method:** both copy the audio into a new file and then call `0xC2BB84D4` with both paths (replace, inference).
  - **CyDrums** has the same chunk code, but no caller of its setters and no slice mode in its manual.
  - **SmplTrek** has CHOP/SLICE but no ORSL chunk; where it stores slices is not traced.
- **Tag search page** (`AppSampleTagSearch`, RTTI; read 2026-11-11). Each audio-file database entry has a 64-bit tag word (`g_audio_file_tags`, `0xC2726160`).
  - **Handler:** slot 11 (app message type 1, acting when msg+4 = 1) reads a bit number from msg+8.
  - **Tag edit mode:** it toggles that bit in the selected file's word (`toggle_file_tag`). "SAVE TAGS" later writes changed words into the files' AFTG chunks.
  - **Otherwise:** it toggles the bit in the page's required-tags mask (+48). With switch bit 16 held, it uses the excluded-tags mask (+56) instead, which is the manual's "Minus" with the page-left switch.
  - **Message type 1** is the page's own pad event, re-posted: `AppSampleTagSearch::on_pad` (slot 7) posts {1, kind, pad, velocity}. It is the only type-1 poster among the 54 `app_post_message` sites.
  - **Slot order:** Lofi-12 XT's controller vtable is ordered differently from SmplTrek's. Encoder is slot 6, and pad is slot 7, confirmed by `TrackColor`, which acts on kind 1 and passes the pad through `pad_to_track`.
  - **So tag bit n = raw pad n.** `pad_to_track` (`0xC2BCD784`) maps even pads 0-14 to tracks 0-7 and odd pads to -1.
  - **Bit-to-tag order (inference):** BD..KB (TRK1-8) would be bits 0, 2, ... 14, and SY..Slice the odd bits, if the odd pads run CFG..RVB in order.
- **Open:** Favorite, the odd-pad order, and the fields of a slice record.

## Interrupts and Swis (2026-11-10; same configuration in all three)

The Hwis are not created at run time (an earlier reading assumed they were). They are static SYS/BIOS Hwi objects in
copy-table data, and the Hwi

- The audio block interrupt is not a Hwi of its own: `audio_block_isr` is EDMA3 completion callback 0, registered with

  12, 14), so 10, 13 and 15 are disabled, and ICR is written `0xFFFF`. ISTP is `0xC16F3C00` / `0xC2DA7400` /

- Swis: exactly two Swi objects exist in each image (scan of the copy-table data for Swi-shaped records), the audio

  posted by `clock_tick`). The only Swi_post call sites are the two in `audio_block_isr` and the one in `clock_tick`.
- So (inference) everything `audio_block_process` calls, the render callback included, runs in a priority-14 Swi,
  above every task and below only the Clock Swi and the Hwis.

## Power management (2026-11-10)

The power manager is a small object without RTTI (`g_power_manager`: SmplTrek `0xC15036E8`, Lofi-12 XT `0xC2B7E65C`,
CyDrums `0xC242F79C`) whose methods are the same code in all three (region_diff over SmplTrek
`0xC1646AC0`-`0xC16470B0` with `--at 0xC2C7A800 0xC2593160`: 431 instructions each, only 18 data-page offsets
differ, GPIO pin constants included). MainDelegate registers itself (its PowerManagerDelegate base, this+24) at
+24 during start-up and sets byte +30 (power key enabled). Field layout: see `g_power_manager` in the symbol file.

Hardware (pin roles inferred from use; `power_gpio_init`, in `.init_array`, takes the pin numbers with
StarterWare numbering, bank * 16 + pin + 1, GPIO base 0x01E26000):

| Pin | Use |
|---|---|
| GP3[0] | power key, active low: held at power-on (`power_on_check`), held over 1 s to switch off (`power_key_poll`) |
| GP4[11] | power hold: `power_on_check` writes 1 once the key has been held about 0.5 s; `power_hold_release` writes 0, which is the last thing the power-off sequence does (inference: the supply latch) |
| GP3[7] | power source: `power_source_read` returns 2 when high, else 1; the battery level is only used while it is 2 (inference: 2 = on batteries) |

Who calls what. `IOObserver::run` (the 1 ms input poll, same code in all three: region_diff shows only moved data,

ticks, `power_low_battery_tick` once per 1024 ticks (count 256) and `battery_sample` once per 1024 ticks (count
1023, eight-sample average, raw values below 2000 ignored). `power_manager_poll` does nothing until +28 (running)
is set; then it reads the source (delegate slot 5 when it changes), polls the power key, checks the auto-off time,
and passes the battery level (delegate slot 1 while on batteries, else -1) to `power_battery_level_set` (delegate
slot 3 when it changes). Input events mark activity (`input_activity_mark` sets +31 before every posted input
event).

MainDelegate's PowerManagerDelegate slots (all six thunks are plain branches, no this-adjust; Lofi-12 XT's slot
bodies are the same code, CyDrums' the same instructions packed differently: region_diff over SmplTrek
`0xC154A0F8`-`0xC154A1F0` shows only branch offsets and padding):

| Slot | Called by | SmplTrek body | What it does |
|---|---|---|---|
| 0 | `power_auto_off_check` | `MainDelegate::power_is_busy` `0xC154A18C` | 1 if any of four checks is non-zero; non-zero counts as activity and postpones the auto power off. Settings. `settings_apply_all` passes BATTERY TYPE to `battery_set_type` (two threshold tables per type, the same
24 bytes in all three; SmplTrek `0xC16CE850` / `0xC16CE970`, raw panel channel 15 values: ALKALINE 2630 / 2830 / 2980 /
3180 and 2730 / 2930 / 3080 / 3280, NiMH 2840 / 2915 / 2940 / 2990 and 2855 / 2930 / 2955 / 3005, LITHIUM 3030 / 3280 /
3360 / 3490 and 3080 / 3330 / 3410 / 3540; names and order from SmplTrek's manual (ALKALINE, NiMH, LITHIUM), the
second set as hysteresis is inference. All three validators accept BATTERY TYPE 0-2, but the Lofi-12 XT and CyDrums
manuals list only Alkaline and NiMH; CyDrums' parameter data still holds ALKALINE / NiMH / LITHIUM labels at `0xC26CA168`
(packed descriptor format, not decoded), so whether type 2 is selectable on those two is not checked) and AUTO POWER OFF to `auto_power_off_apply`, which sets the timeout: 1 = 30 min (Lofi-12 XT:

code postpones the auto power off, and `power_hold_release` is the last step of the power-off, after the settings
save. `power_on_check` writes GP4[11] = 1 only when the key is still held (GP3[0] low) through ten 50 ms checks, and
returns 0 without touching the pin when the key is not held at entry (2 is returned only when byte +28 shows it
already started; simulated, `analysis/input_map.py`). The supply is held anyway: BOOT 1.0.17 latches GP4[11] before
it jumps into SYSTEM (claim HW-24, seen on the unit in device session D0,
`experiments/sessions/D0-hang-recovery.md`).

## SD card (2026-11-10)

The SD layer is the same code in all three products (region_diff, only moved data addresses and data-page offsets:
diskio `0xC1682320`-`0xC16824E0`, the SD driver `0xC1645FA8`-`0xC16463D0`, the card manager `0xC16724A0`-`0xC167277C`,
the MMCSD wait/post helpers `0xC166F900`-`0xC166F98C`, the card-reader mode functions `0xC1678D60`-`0xC1678E4C`;
`mmcsd0_isr` was already verified). SmplTrek addresses below; the others are in the symbol files.

Start-up. `sd_driver_static_init` (`.init_array`) builds `g_sd_driver` (`HAL::SDDriver`, `0xC15051E4`);
`sd_card_gpio_init` (`.init_array`) takes GP4[0] (card detect) and GP4[1] and clears the card observer. MainDelegate
start-up calls `sd_card_hw_init` (`0xC167270C`): pin mux for the two pins, GP4[0] input, GP4[1] output driven 0,
`HAL::SDDriver::start` (once: MMCSD0 base 0x01C40000, EDMA3Init on CC0, EDMA3 channel requests, the controller info
`g_sd_ctrl` at `0xC14B63A8` (once mistyped here as `0xC14963A8`; HW-25 and `sd_map.py` have it right), controller init) and `sd_set_card_detect(sd_card_detect_raw)` (GP4[0] low = card present).

FatFs to hardware. FatFs (R0.14a-R0.15a, see `f_mount` in the symbol file; drive 0 only) calls the diskio functions, which call `g_sd_driver`'s methods
directly (devirtualised): `disk_read` -> `HAL::SDDriver::read` (vtable slot 2), `disk_write` -> `HAL::SDDriver::write`
(slot 1), both -> `sd_transfer(buff, sector, count, op)` with op 2 / 1, which calls the protocol layer on `g_sd_ctrl`
(read `0xC15D2288`, write `0xC15D1FF4`; argument order as in TI StarterWare's AM335x `mmcsd_proto` MMCSDReadCmdSend /
MMCSDWriteCmdSend, but that layer is not in the C6748 package, so the origin is unconfirmed). A transfer result of 1
means success (disk_read / disk_write return RES_OK, else 4). `disk_status` returns 0 when the detect callback reports
a card, else 3; `disk_initialize` resets the driver and runs the card initialisation (op 0).

Interrupt. `mmcsd0_isr` reads the MMCSD0 interrupt status, calls per-bit callbacks from a table at `0xC16EFBA0` (its
setter `0xC166F978` has no direct caller) and posts the SYS/BIOS Event `0xC14FFD54` with the status in B14+1120;
the transfer code blocks in `mmcsd_wait` (Event_pend, no timeout). So SD transfers run in the calling task and sleep
until the ISR signals completion (inference from the pend/post pair). Per-bit dispatch simulated 2026-11-14
(04-hardware-access.md, "Controller layer"): with the listener table empty, as in the stock app, the ISR posts only on
RSPDNE for a command without data.

Insert and removal. `IOObserver::run` calls `sd_card_poll` every 64 ticks. An insertion is reported after the card has
read present for more than 500 ticks; a removal at once: the card-reader side is told (`0xC1678E04`), the driver is
reset and the observer called with 0. The observer is a static `std::function<void(unsigned)>` (`g_card_state_observer`
`0xC1503E90`), set by MainDelegate start-up to the `handleCardStateEvent` lambda (`0xC1684AE0`; Lofi-12 XT `0xC2CBA700`,
CyDrums `0xC25D0140`). The lambda mounts (`card_mount`: `f_mount(&fs 0xC14F6600, path, 1)`) or unmounts (`card_unmount`)
and posts app message type 2 with the event. It runs in the IOObserver task, so the mount happens there, not in the
main task. CyDrums' mount function does more after `f_mount` (product code, not read). The power-off handler replaces
the observer before shutting down.

Card-reader (USB mass storage) mode, inference from its callers (AppSDReader, AppTestUSBMSC): `usb_msc_mode_set(1)`
after `card_unmount`, `usb_msc_mode_set(0)` on exit; while it is on (B14+444), `MainDelegate::power_is_busy` reports
busy through `sd_card_reader_active`, so the unit does not switch itself off.

## USB (2026-11-10)

Same code in all three products (region_diff: `usb0_isr`, USB0DeviceIntHandler `0xC16A1940`, USBDeviceIntHandlerInternal
`0xC158EA24`-`0xC158EC26`, `usb_task_dispatch` `0xC158E70A`-`0xC158E8F0`, the task post/set functions `0xC168B1E0`-`0xC168B2E4`
and the USB-MIDI class block `0xC162D774`-`0xC162DFDA`; only moved data addresses and data-page offsets). The
MIDIStreamUSB and USBAudioEnvetReceiver virtuals (and HAL::SDDriver's) also match in all three (func_match
similarity >= 0.9).

Origin. The interrupt path is TI StarterWare 1.20.04.01 usblib: `USB0DeviceIntHandler` has the body of
`usblib/device/usbdhandler.c` (C6748 branch: INTR_SRC 0x01E00020, clear 0x01E00028, IntEventClear(19),
`USBDeviceIntHandlerInternal(0, status, NULL)`, END_OF_INTR 0x01E0003C), and `USBDeviceIntHandlerInternal` follows
`usbdenum.c` with the tCustomHandlers offsets of StarterWare's `usblib.h` (suspend +28, resume +32, disconnect +36,
endpoint +40, device +44). The usblib core matches (by body here, and byte for byte for the unchanged files: "Compiler,
runtime and SYS/BIOS versions"); an earlier "StarterWare usblib does not match" came from comparing the USB-MIDI class
code, which has no usblib counterpart.

Sonicware's changes: `usb0_isr` (the static Hwi) only tail-calls the handler at B14+1184, which `usb_dcd_init` sets to
`USB0DeviceIntHandler` (StarterWare would IntRegister it). EP0 (enumeration) is not handled in the interrupt: it is
posted to the USB task as code 0x80000001. The class endpoint handler gets a third argument saying where it runs (2 from
the interrupt, 0 / 3 / 4 from the task). Posts from interrupt context use `usb_task_post_nowait` (Mailbox_post with
timeout 0) on the USB task's mailbox (B14+1440); `usb_task_loop` passes each {code, arg} to `usb_task_dispatch`.

USB MIDI receive path:

| Context | Step |
|---|---|
| USB0 Hwi | `usb0_isr` -> `USB0DeviceIntHandler` -> `USBDeviceIntHandlerInternal` -> `usb_midi_endpoint_handler(dev, status, 2)` (`0xC162DE70`) -> endpoint status and bytes available, then dev+12 (`0xC164AC00`, usblib `USBBufferEventCallback`, exact match 2026-11-14) with the receive `tUSBBuffer` `g_usb_midi_rx_usbbuffer` (2 KiB ring at `0xC14E3EA8`) and event 2 -> the buffer's callback `usb_midi_rxbuf_callback` posts {0, 0x10000 << endpoint} |
| USB task (priority 14 SmplTrek, 13 Lofi-12 XT / CyDrums) | `usb_task_loop` -> `usb_task_dispatch` -> `usb_midi_endpoint_handler(dev, mask, 0)` -> dev+16 = `usb_midi_rx_callback(dev, 2, ...)` -> `MIDIStreamUSB::receive` (USBMIDIDelegate slot 0) -> CIN table -> `MIDIInputPort` -> MainDelegate's MIDIInputPortDelegate handlers |

So USB MIDI input, including MainDelegate's MIDI handlers for USB, runs in the USB task, not in an interrupt (static
reading; not observed on hardware). DIN MIDI is parsed in the MIDI UART task, so USB and DIN input reach MainDelegate
from different tasks. Anything that blocks on the USB receive path delays all USB work while it does.

### USB audio sample path (2026-11-14, simulated)

SmplTrek 3.2.174, run in c6sim (`analysis/usb_audio_map.py`, `test_usb_audio_map.py`). Event codes are usblib's
(`usblib.h`: 1 USB_EVENT_DISCONNECTED, 2 USB_EVENT_RX_AVAILABLE, 5 USB_EVENT_TX_COMPLETE, 14
USB_EVENT_COMP_IFACE_CHANGE). Each direction has a StarterWare-layout `tUSBBuffer`: receive `0xC16CB350`
(callback `0xC15E92A0`, buffer `0xC14EE430`, 0x480 bytes) and transmit `0xC16CB374` (callback `0xC15E8DA4`,
buffer `0xC14EE8B0`, 0x480 bytes), both on the audio device `0xC16C8C9C`.

| Step | Computer -> unit (interface 1, EP1 OUT) | Unit -> computer (interface 2, EP2 IN) |
|---|---|---|
| On/off | event 14 `{interface, alt}` on `0xC15E92A0` sets B14+764 = alt; start re-initialises the receive buffer (`USBBufferInit`) and calls delegate slot 0, stop slot 1 | same, B14+768; start re-initialises the transmit buffer, sends a zero-length packet, delegate slot 2; stop slot 3 |
| USB side | event 2: `0xC15E91E0` reads every waiting byte into a 1152-byte ring at `0xC14EED30` (write offset B14+760). No check against the read offset: more than 1152 unread bytes overwrite the oldest | event 5: if packets are queued (read index `0xC14C90B0` != write index `0xC14C90AC`, ready byte `0xC14C90B8`), sends the next 192-byte packet through `0xC162A6E8`; otherwise a zero-length packet |
| Audio side | once per 128-frame block, `audio_fill_input_block` -> `0xC168F01C` -> `0xC15E99D0` copies 128 frames (read offset B14+756) to `0xC14F19F8` as int32 `sample << 16`, L then R per frame. Fewer than 512 bytes waiting, or B14+764 clear: nothing is copied and the block keeps the previous 128 frames | after the mix, `0xC159B548` -> `0xC168F014` -> `0xC15E9580` (only while B14+768 is set): L[128], R[128] floats * 32767.0, truncated, stored as int16 (no clipping: 3.0 becomes 32765) into 32 packets of 192 bytes (48 frames, 1 ms) at `0xC14C78AC` |
| Consumer | `TrackSound::USBTrack::render` gets the block from `0xC168F048` and renders it as track 13 (USB AUDIO) | the host |

The delegate is the USBAudioStreamingDelegate at B14+772 (`g_usb_audio_event_receiver`). While either flag is
set the class keeps the TIMER64P1 trim loop armed (`0xC1661230`); `0xC16612E0` disarms it when both are clear.
Event 1 (disconnected) clears both flags. 0xC001 (USBD_AUDIO_EVENT_ACTIVE in the PDK's numbering) is ignored.

When the track hears it (simulated, 2026-11-14). `TrackSound::USBTrack::render` reads the block only while the
track's flags word (+8) is above 31, that is, while bit 5 ("playing") is set. Bit 5 is set by the track's vtable
slot +24 (`0xC15EB8C8`), reached through `tracks_start` (`0xC15AA9E0`; a track index, or -1 for all 15). The app
pages (audio input setting, sample recording, the track edit pages, FX setting) call it as a play toggle: when
`track_is_playing` (`0xC15A9D8C`, bit 5; index -1 = any track) is false they call `tracks_start`, otherwise
`tracks_stop` (`0xC15AA8E0`). Stop (slot +32) only sets bit 1 and a request byte; on the second render block after
it, render stores 2 and the track stops. So computer audio reaches the mix only while track 13 is playing,
whatever the interface state. The user-facing control is the USB AUDIO track's pad (SmplTrek v3 Reference Manual pp. 136-137). The USB SETTING
screen's HOLD/GATE option decides it: HOLD toggles the track on each press, GATE keeps it on only while the pad is
held. In code, `tracks_start` is reached from several places (2026-11-14, static):
- the play toggles of the mixer, audio input setting, sample recording and FX setting pages (slot +32 message
  handlers, each testing `track_is_playing` first);
- `handle_track_cc` (MIDI control change per track);
- Sequencer callbacks: `Sequencer::SequencerDelegate` slots 0 and +40, and `Sequencer::SequencerPlayerDelegate`
  slot +8 (thunks from MainDelegate's secondary vtables), each with a track index.
HOLD/GATE (PREX +36) is read by the track play toggles ("PREF fields"); which of these paths the pad press itself
takes was not traced (the pages' message dispatch lies in between). The delegate does not touch the track. It is the static `USBAudioEnvetReceiver`
object `0xC16DB68C` (RTTI name as spelled; installed by `usb_start` `0xC168EFE4`). Its slots 0, 2 and 3 do
nothing, and slot 1 (interface 1 stop, `0xC16A66A0`) is memset(`0xC14F19F8`, 0, 1024), which clears the block.

Second ring reader (simulated). `0xC15E970C` reads the same ring with (chA, dstA, dstB, chB, n). Per frame it
stores sample chA (0 = L, 1 = R, negative = skip) at dstA and sample chB at dstB, as int32 `<< 16`, each pointer
advancing 8 bytes. Like the pull, it copies nothing while fewer than n frames are waiting. It is a channel-select
variant of the pull, not rate matching (an earlier inference). Nothing calls it, branches to it, or
holds its address. That is true in 3.2.174, 3.0.148, 1.0.65, Lofi-12 XT 1.5.205 and CyDrums 1.1.84, where it is
always push + 0x18C, so it is unused code in these builds.

Consequences (inference): after an underrun while streaming and playing, the USB track renders its last 128 frames
again until the pull succeeds; only an interface-1 stop clears the block, so an underrun repeats audio rather than
going silent. The OUT ring holds 6 ms. The block size and the 1 ms packet rate
are fixed in the code, at 48 kHz 16-bit stereo only.

Origin: the descriptor layout resembles the PDK's `usbdaudio.c`
(pdk_omapl138_1_0_11). That layout is common to UAC1 speaker+microphone devices, though. The PDK class takes buffers
from the app (`USBAudioBufferOut`) and moves the data with CPPI DMA, while the stock code uses a `tUSBBuffer` per
endpoint and the composite interface-change event. So the stock audio class is not that file (an earlier lead); its origin is open.
The function names in this section are descriptive and not in the symbol file.

## Hardware use per product (2026-11-19)

How Lofi-12 XT 1.5.205 (LF), CyDrums 1.1.84 (C1) and CyDrums 2.0.97 beta (C2) drive the board, against SmplTrek
3.2.174 (ST). Static reading of the objdump listings, `region_diff`, caller censuses and c6sim runs through scratch
wrappers around the repo tools (the CyDrums 2.0.97 listing and func_match file were built for this pass; neither is
in the repo). Lofi-12 XT 1.5.205 was also imported into Ghidra (scripts in `ghidra/scripts/`; projects are local, not committed).
Claims XF-20 to XF-25.

**Summary.** The hardware layer is the same code in every product and every release. No product reads a pin, writes a
codec register, sends a panel command or addresses a peripheral that SmplTrek does not. What differs is product code
deciding when the shared helpers run.

### The hardware layer across all 13 releases (XF-20)

SmplTrek 1.0.65, 1.1.72, 1.2.86, 1.3.90, 1.4.99, 2.0.129, 3.0.148, 3.2.174; Lofi-12 XT 1.1.156, 1.2.179, 1.5.205;
CyDrums 1.1.84, 2.0.97 beta. In every image:

| Item | Count | Notes |
|---|---|---|
| `gpio_pin_number` set-up sites | 31 | same (bank, pin) constants, all resolved |
| direction calls | 28 | 26 outputs, 2 inputs (GP3[8], GP4[0]) |
| `gpio_write` sites | 46 | |
| `gpio_read` / `gpio_read_bank16` sites | 17 / 6 | single-pin inputs read: GP3[0], GP3[7], GP3[8], GP4[0]; bank reads GP3, GP5 (keys, encoders); the rest read back outputs |
| GPIO interrupt calls | 3 `GPIOIntTypeSet`, 1 status, 1 clear | bank 7 (SYNC IN) is the only GPIO interrupt |
| direct GPIO base sites | 12 | same functions |

GP3[8] is the only jack-like input in every release; no image touches the codec's headset-detect registers (13, 14,
96, 97). `hw_inventory.py` finds the same peripherals at the same addresses in all 13 (USB0 code in 1.0.65 has 74
sites against 62 later). The one change: up to SmplTrek 2.0.129 `codec_adc_hpf_init` ends with register 12 = 0x50
(ADC high-pass on); from 3.0.148 the audio start writes it through `0xC161DE80` instead (87 → 86 `codec_write`
sites). Lofi-12 XT 1.1.156 already has the later form. A jack sensed by the panel MCU would arrive over UART1, not as
a pin read; the panel link is covered below.

### Audio (XF-21)

- **Shared code, C2 included** (region_diff, 0 real differences): the codec functions `0xC161D560`-`0xC161DF84`
  (LF `0xC2C5B8C0`, C1 `0xC25766A0`, C2 `0xC25F31C0`), the codec wrappers, the input actions, gain appliers,
  `pad_apply` and jack watcher `0xC15F0E80`-`0xC15F12E8`, the per-pin helpers (ST + 0x1635160 in LF, + 0xF4C6A0 in C1,
  + 0xFCCFE0 in C2), `codec_i2c_init` / `mcasp_configure` / `audio_start`, and the clock-probe area.
- **Codec registers.** `codec_write` has 86 sites in every image, all in the shared block, with identical
  per-function counts; its I2C transfer has one caller. The headphone and COM drivers (47, 51, 54, 58, 71) and the
  DAC1 routes to LEFT_LOP (82, 85, 92) stay uncalled everywhere, so HW-15 holds in every product.
- **Mutes.** GP2[8] is driven only by SPEAKER MUTE (+0x48 in all) and the factory test page; GP2[9] only through
  `0xC1678640` (start-up, power-off, test page). No product drives either from source, monitor or jack state.
- **Input source model.** ST has one REC SRC number (0-25, +0x10). LF and C1 use a pair, source 0-6 and level 0-2,
  applied by one selector (LF `0xC2BCDDEC`, C1 `0xC24ED0EC`) that stores them at +0x158 / +0x15C and calls ST's
  four setters and `pad_apply`. Simulated for source 0-7 × level 0-2, every pair lands on exactly the codec, pin and
  slot state of a ST REC SRC:

  | Source | Level | ST equivalent |
  |---|---|---|
  | 0 | any | 0 built-in mic |
  | 1 | 0 / 1 / 2 | 1 / 2 / 3 Hi-Z L |
  | 2 | 0 / 1 / 2 | 4 / 5 / 6 dynamic mic R |
  | 3 | 0, 2 / 1 | 7 stereo line / 8 with PAD |
  | 4 | 0, 2 / 1 | 9 mono line / 10 with PAD (planes stay (1,1); ST forces (1,2) through +0x24) |
  | 5 | any | 11 USB |
  | 6 | any | resample (ST 12-25; same codec and pins) |
  | 7+ | | falls back to 0 |

  The names come from Lofi's file prefixes `BIM GTR MIC MIX INL USB RSM` (`0xC2D8C579`) and the equivalence. The PAD
  is level 1 on sources 3 and 4; the selector does not set ST's +0x24. Lofi turns monitoring off (+0x28 = 0) on
  source 6. **+0x158 is therefore the input source**, which explains the USB track render reading it: at value 5
  (USB) Lofi's render takes buffer `0xC2B6F660` in place of the USB block.
- **Who selects.** LF: `AppSampleRecording` (source clamped to 0-6). C1: only `AppExtSrc`, source clamped to 0-4
  (no USB or resample), so CyDrums 1.1.84 switches the codec only for EXT SRC monitoring. C2: two pairs, EXT SRC at
  +0x158 / +0x15C and a new sampling pair at +0x64 / +0x68, chosen by a mode byte B14+696; entering the sampling page
  (`0xC2564F44`) applies the sampling pair and leaving (`0xC256588C`) restores EXT SRC. C2's USB source adds a
  channel choice: level 0 = L (planes (1,1)), 1 = R ((2,2)), 2 = L+R ((1,2)). That is the only new route. Field
  labels for +0x28, +0x64 and +0x68 come from use, not from page labels.
- **GP3[8].** Every product keeps the shared change watcher (on change: a screen refresh only) and the rule that the
  built-in mic is monitored or used only while GP3[8] reads high: ST `audio_mix_input_monitor`, LF `0xC2BB7458`, C1
  and C2 in `TrackSound::ExtTrack` slot 3 (`0xC25882E8`, `0xC2606868`). C2 adds the same rule to its sampling input
  path (`0xC2537224`). Only SmplTrek draws the title-bar mic icon.
- **McASP / EDMA.** The only change is the block size (frame constants 64 → 48 and a 16-pass loop → 12 in
  `audio_block_isr` / `audio_block_process`, the same in LF, C1 and C2); everything else is identical.

### Panel MCU link, pads, LEDs, keys (XF-22, XF-23)

- **The link is the same everywhere, C2 included.** `ADControllerUART` differs only in the task priority constant.
  The DSP sends the same one-byte commands (`90 91 B0 B1 B2 A0 C2`, from the same number of call sites) and the LED
  command (`panel_led_command`, 19 callers in each); it parses only `Bn` and `A1`. Idle-byte slot 0 is empty in all;
  nothing reads A1 bytes 0-2 or the stored pad channel array; the MCU version bytes are read only by
  `mcu_version_string` for SYSTEM INFO, so no product branches on the MCU version. No aftertouch, extra sensor or
  configuration command exists on the link.
- **Pads, common.** Press at ≥ 800, sent on the next sample with velocity from the higher of the two samples;
  release after 4 low samples (ST, LF) or 10 (C1, C2) below 100. All 15 channels are pads in every product.
- **Lofi-12 XT pressure** (`pad_sensor_update` `0xC2C69F54`, simulated). Per-pad 52-byte record: +0 pressure, +36
  last sent, +40 countdown, +44 baseline, +48 active flag. A press sets the countdown to 40 samples (about 150 ms);
  at 1 the raw value becomes the baseline; raw > baseline + 200 sets the flag until release. Every sample the raw
  value goes through `pad_velocity_from_curve(raw, 3)` (curve 3 hard-coded) and the pressure is the mean of the last
  9 values / 127. While the flag is set, a change of more than 1/127 calls KeyPadDelegate slot 3 with a float 0-1;
  MainDelegate forwards it to the current page's vtable slot 10 (which pages implement it is open). Lofi's
  `g_pad_velocity_curves` (`0xC2D87168`) holds **four** curves: 0-2 as ST, 3 (`0xC2D87768`) Lofi-only and steep at
  the bottom (800, 1277, 1401 ... 3200).
- **CyDrums aftertouch** (`pad_sensor_update` `0xC25A7B84`, C2 identical). KeyPadDelegate slot 1 gets the pad and a
  0-127 value on every sample while the pad is held (about 262 per second per pad), with no change filter in the
  sensor code. The handler `0xC24CD4A0` maps the pad to its track and builds `0xD0 | channel, value` (the channel
  word − 48), then `0xC2578014` passes it to `g_midi_stream_pad` (`0xC2430078`, `MIDI::MIDIStreamPAD`), the pads'
  internal MIDI stream. It re-enters the app's own MIDI input: `MIDIInputPort` → slot 4
  `on_midi_channel_pressure` → `0xC24E2970` per matching track, which calls only track and voice code (no MIDI
  sender). So pad pressure is internal aftertouch for CyDrums' sound engine and does **not** go out on DIN or
  USB-MIDI (a first reading took `0xC2578014` for a MIDI send; the emulator saw no 0xD0 on UART0 with a pad held).
  Settings VELO CRV +0x164, AT THRS +0x16C and AT CRV +0x170 exist; which applies
  where is open.
- **Velocity curves.** CyDrums' table (`0xC2686308`, C2 byte-identical) has a CyDrums-only curve 0, then ST's 0-2 as
  1-3. At the start-up index 2, CyDrums uses ST's curve 1 and Lofi ST's curve 2: raw 2000 gives 63 in CyDrums and 43
  in Lofi.
- **LEDs.** The same 115 addresses in all four images. LF and C1/C2 drive button LEDs from a few functions
  (`AppLEDDelegate`, PrivateLEDTask; ST has neither). CyDrums never lights FUNC, MIXER, HOME, REC or PLAY outside the
  clear-all; Lofi has a five-entry red/green setter table at `0xC2DB656C` (user not traced). The TEMPO LED in mode 1
  is blue in ST and LF but amber (red 5, green 2) in CyDrums (`0xC25DFA2C`).
- **Keys and encoders.** `ControlScan`, `encoder_read_phases` and `gpio_read_bank16` are identical in all four; no
  extra key bits. LF, C1 and C2 use `RotaryEncoderV2`.

### SYNC, MIDI, USB, power, other buses (XF-24, XF-25)

- **SYNC.** The GPIO layer (15 ms pulse, 60 ms lockout, POLARITY IN +0x08, OUT +0x0C) is the same in all. LF and
  C1/C2 count 96 steps per quarter note (ST 72), send MIDI clock every 4 steps and start a SYNC OUT pulse at steps 0
  and 48; SYNC IN feeds 48 steps per edge (ST 36). So both directions stay 2 PPQN in every product (inference from
  the constants, as HW-31). CyDrums feeds SYNC IN edges without the export check ST and LF make.
- **MIDI transmit.** DIN and USB-MIDI carry the same messages in every product (OUT TO picks the ports). **Lofi alone
  sends Song Position Pointer** (`0xC2C59E20`: a 14-bit value split into two 7-bit bytes, 3 bytes, gated by
  `midi_tx_spp_enabled`; its one caller sits next to the CONTINUE calls). **CyDrums' tx-allowed check returns 1**
  (`0xC24EE304`, C2 `0xC2565DB4`), so CyDrums never blocks MIDI output during an audio export; ST and LF do. CyDrums
  has no plain program-change sender.
- **USB.** The assembled configuration descriptor (simulated) is 234 bytes and byte-identical in all four images;
  only the product strings differ. The class code is identical. The sample path differs only in the 96-frame block
  (the push takes a constant 96; the pull is called with 96). LF and CyDrums have no USB TRACK SETTING page (no
  HOLD/GATE).
- **Power.** The power manager and the battery threshold tables are identical in all four (ALKALINE, NiMH, LITHIUM
  labels exist in all). AUTO POWER OFF: value 1 is 30 min in ST and C1, 20 min in LF and C2 (CyDrums 2.0.97 changed
  it, string "30min" → "20min"); values 2-4 are 1 h, 3 h and 6 h everywhere. GP3[7] is read by the power manager and
  the title-bar drawer in every product.
- **Other buses.** I2C1 is unused everywhere (the I2C open has one caller, instance 0). No product addresses EMIFA,
  TIMER64P2 or TIMER64P3. TIMER64P1 is the USB audio trim loop only (identical code). CyDrums' extra census constant
  `0x01E802DC` is not a peripheral address.

### SmplTrek 2.0.129 against 3.2.174

Product logic compared the same way (region_diff, caller sets, data bytes; not simulated: 2.0.129 has no sim_boot
entry). The same in both: the REC SRC range 0-25 and `rec_src_select`, `pad_set` / `pad_on` / `pad_apply`, the
input appliers and dispatcher, all four GP3[8] users (title-bar icon included), the GP2[8] / GP2[9] callers, the
panel commands and `led_set` callers, pad thresholds and curves, SYNC (72 steps, 2 PPQN), MIDI clock / start / stop /
CC gating, the USB audio path with HOLD/GATE, the power values and the 128-frame block. Differences:

- **PAD at start-up.** 3.2.174's start-up settings apply (`0xC158B780`) calls `pad_apply(pad_on())` between the
  input setters and SPEAKER MUTE; 2.0.129's (`0xC159A060`) has the same sequence without it (`pad_apply` 10 callers
  against 9). Inference: in 2.0 a saved PAD-on setting does not reach GP1[3] and the line routing at power-on until
  the REC SRC page applies it (perhaps the 3.x note "audio not reflected after restarting").
- **Program Change.** 2.0.129 has two PC senders (`0xC1620E14`, `0xC1620F28`) gated by a non-zero word at
  `0xC150F5B0` (inference: g_settings+0x114); 3.2.174 gates on `g_midi_settings[2]` being 2 or 3 and adds TX SCENE
  CHANGE (`0xC1619438`). 2.0.129 has no PC receive or scene handling; its PREF block is 280 bytes.
- The codec register 12 move (above): 2.0.129's `audio_start` (`0xC162A8D4`) takes no argument.

## Compiler, runtime and SYS/BIOS versions (2026-11-09, 2026-11-14)

Found by matching TI's prebuilt libraries against SmplTrek 3.2.174 function by function (`analysis/lib_match.py`:
relocated words masked, same 32-byte alignment phase, size-0 assembly symbols sized to the next global symbol).

- **TI C6000 code generation tools 8.3.11-8.3.13.** Every CGT 8.3.9-8.3.13 and 8.5.0 `rts6740_elf.lib` was
  tested. Unique matches: 8.3.9 and 8.3.10 140 functions (22.4 KB; their RTS code is byte-identical),
  8.3.11 / 8.3.12 / 8.3.13 146 (26.4 KB), 8.5.0 114 (11.5 KB). Of the 149 functions changed from 8.3.10 to
  8.3.11 the firmware has the new form of 8 (cosf, powf, tanf, `__c6xabi_divlli`, `_pconv_e`, `__TI_readmsg`, ...)
  and the old form of none except fcvt (which matches both). Of 909 changed from 8.3.13 to 8.5.0 it has the 8.3
  form of 37 and the 8.5 form of 1. The 18 functions changed in 8.3.12 / 8.3.13 (add_device, the malloc/free
  family, `__c6xabi_divd`, libc++ debug/ios internals) do not occur at all (the heap is SYS/BIOS's), so
  8.3.11-8.3.13 cannot be told apart from the RTS; the matching here uses 8.3.13 (`-mv6740 --abi=eabi -O2`). The
  image holds no tool version strings. The StarterWare match (next bullet) narrows the options to `-O2`.
- **TI StarterWare 1.20.04.01 (claim LIB-1, 2026-11-14).** Its sources (usblib core, drivers) rebuilt with CGT
  8.3.9-8.3.13 `-O2 -mv6740 --abi=eabi` match 115 stock functions byte for byte (relocated fields masked): all of
  usbbuffer, usbringbuf, usbdcdesc and usbdesc; half of drivers/usb.c; four CPPI 4.1 DMA helpers (cppi41dma.c, so the
  USB stack uses CPPI DMA); and parts of edma, gpio, timer, interrupt, uart, mcasp, i2c and psc. 8.3.2 gives 49 of the
  53 usblib matches and `-O3` gives 21, so the build was `-O2` with 8.3.9 or later; with the RTS result that is CGT
  8.3.11-8.3.13 `-O2`. usbdenum, usbdhandler, usbdconfig, usbdcomp and usbtick do not match byte for byte: those are
  the files Sonicware changed (task posting; usbdhandler and usbdenum still match by body, section "USB"). The USB audio and MIDI class
  code has no StarterWare, AM335x StarterWare or PDK counterpart: AM335x StarterWare has CDC, bulk, HID, MSC and
  composite device classes only, and the PDK's `usbdaudio.c` is a different stack. Result file (local, not
  committed): `work/smpltrek-3.2.174.starterware-8.3.13.libmatch.json`; 99 of the 115 are not in the symbol
  file.
- **Names (claim LIB-2).** The unique 8.3.13 RTS matches are in `symbols/smpltrek-3.2.174.json` (71 added, so 72
  of 76 addresses named with operator new). The other four each hold identical-code C++ destructors or
  constructors (D0Ev, C2Ev) that the bytes cannot tell apart. Exact matches in the other images are in the
  `symbols/hand/` files.
- **`__TI_printfi`** (0xC1577B00, probable): its only caller is the exact TI sprintf (0xC16A11C0) and it calls
  the exactly matched printfi helpers, including `_pproc_v_fgea`, which only `_printfi_vector.c` defines. Its body
  matches no CGT 8.3.9-8.3.13 or 8.5.0 RTS byte for byte, so it is not version evidence.
- **SYS/BIOS 6.76.03.01 (claim LIB-3).** Built by configuro as a custom library with 8.3.13
  (`analysis/sysbios_match.cfg`, a guessed configuration with logging off), it matches 69 kernel functions
  exactly; the prebuilt xdc.runtime library matches 44 more. The firmware entry is the XDC/SYS-BIOS boot routine
  (clears IER/CSR, calls three hook pointers), not the RTS `_c_int00`. Still unnamed: the configuration-dependent
  functions (Task_sleep, Semaphore, Clock, Queue), which need Sonicware's exact settings or another SYS/BIOS
  release. Similarity matching (`src_match.py`) misassigns too often on this whole-program build to be used alone.

## Known differences

Each item says how it was checked.

- Audio block: 128 frames (SmplTrek) versus 96 (Lofi-12 XT, CyDrums); region_diff ("Audio engine interface").
- Task priorities: SmplTrek 13-15 for the platform tasks, Lofi-12 XT and CyDrums one lower with their pattern task at
  15 (read at the call sites; "Tasks").
- SYS/BIOS block around `mailbox_pend`: different in CyDrums (region_diff).
- Settings layout: PREF 284 / 404 / 376 bytes; Lofi-12 XT and CyDrums have SmplTrek's fields 4 bytes later from the
  per-track channel array on (read from the validators; "PREF fields").
- MIDI receive: CyDrums has a ninth delegate slot (channel pressure at slot 4) and every later slot one higher
  (dispatcher read packet by packet; "MIDI receive").
- AudioFileControlTask: Lofi-12 XT and CyDrums drop SmplTrek's no-op command 6 (later numbers one lower), always open
  synchronously, and use larger stream objects; CyDrums skips the card space check after writes (read in each
  product; "Audio file commands").
- CyDrums' `uart_isr` is scheduled differently (same constants; region_diff).
- AUTO POWER OFF value 1: 30 min in SmplTrek and CyDrums 1.1.84, 20 min in Lofi-12 XT and CyDrums 2.0.97
  (`auto_power_off_apply`); the power-off message handler is compiled differently in each product (same tail;
  "Power management").
- Hardware use (2026-11-19, product code read and simulated; "Hardware use per product"): input selection by a
  (source, level) pair in Lofi-12 XT and CyDrums; Lofi pad pressure and Song Position Pointer; CyDrums pad
  aftertouch (internal, through `g_midi_stream_pad`), an always-true MIDI tx-allowed check and an amber TEMPO LED in
  mode 1; 96 sequencer steps per quarter note in Lofi and CyDrums (SmplTrek 72).
- Application code: 33 identically laid-out blocks have real differences; most are app classes, std:: and Sequencer
  code (region_diff; list in `03-platform-shared.md`).
