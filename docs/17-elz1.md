# Original ELZ_1: static profile of the seven releases (v2.0 to v7.0)

Static analysis only, 2026-11-23. Inputs: `firmware/other/ELZ_1 v2.0.zip` ... `ELZ_1 v7.0.zip` (legacy container, INT-15).
v7.0 is described in depth; the other releases are given as differences, and every fact marked "all seven" was
checked in each image by the script named. Addresses are v7.0 unless stated. "Not found by this method" means
the named tool or scan did not see it, not that it is absent.

Session scripts named below are in `analysis/other_products/elz1/` (single-purpose and unmaintained; its README lists
their inputs); each fact also names the repository tool or the address to re-check it. Intermediate files: ELFs
`elz1-<v>.elf` (mmtd2elf), objdump listings `dis-<v>.txt`. Scripts:
`container.py` (container and pmtd listing), `secs.py` (section reader), `copytab.py` (decodes the TI copy table:
rle24 and zero-init records), `findinit.py` (finds `__TI_auto_init`'s four table constants), `xrel.py` (the
cross-release checks), `tasks.py`, `usb2.py`. MVK/MVKH pairs were combined in code as
`((mvkh>>16)<<16)|(mvk&0xffff)`.

**Container** (`container.py`). Header `cmtd`, product word 1, zero, CRC, descriptor count (INT-15).
v2.0-v5.0 and v7.0 carry two descriptors (kind 2 PRESET `pmtd`, kind 3 SYSTEM `mmtd`); v6.0 carries three (kind 1
BOOT 1.0.10, already in `docs/05-bootloader.md`). No release carries the modern layout or per-product seeds
(INT-15); v7.0 (June 2023) is still the legacy layout.

**mmtd sections (v7.0)**, six in every release, same roles in all seven:

| # | v7.0 range | size | role |
|---|---|---|---|
| 0 | 0xC139E3F8-0xC141B478 | 0x7D080 | copy-table load data (compressed initialised data + the table itself) |
| 1 | 0xC139E200-0xC139E3F8 | 0x1F8 | small (vector/boot-time data, not analysed) |
| 2 | 0xC139E000-0xC139E200 | 0x200 | small (not analysed) |
| 3 | 0xC10A1C00-0xC11FB100 | 0x159500 | `.text` (holds the entry) |

| 5 | 0xC139BAD4-0xC139D84C | 0x1D78 | small const/data block below B14 |

**Run-time layout from the copy table** (`copytab.py`, constants found by `findinit.py`). v7.0
`__TI_auto_init` at 0xC11E2020 (called from `_c_int00`, 0xC11ECBC0 branch to 0xC11E2020) loads handler table
0xC141B418-0xC141B424 (three handlers: 0xC11E7040, 0xC11FA800, 0xC11FA7E0) and records 0xC141B440-0xC141B478
(seven records). Decoded: handler 1 = rle24 for 0xC11FB100 (+0x11DDCB, `.far`/`.data` after `.text`), 0xC139DE04
(+0xDA), 0xC139DC90 (+0x172), 0xC10A1B18 (+0xE8); handler 0 = zero-init for 0xC139D850 (+0x43B, the B14 page),
0x11F00000 (+0x1204, L1D RAM) and 0xC0000000 (+0x10A1B14: 16.6 MiB of zero-filled DDR below `.text`). B14 =
0xC139D850 (`_c_int00` 0xC11ECB78/0xC11ECB7C); boot stack top 0xC2C01FFC (0xC11ECB6C/0xC11ECB70). Same seven-record
shape in all seven releases (`xrel.txt`), except that in v3.0 and v4.0 the L1D record is rle24 (initialised,
0x1008 bytes) instead of zero-init.

**PRESET (pmtd) content partition, kinds and sizes only** (`container.py`): pmtd 2.0.30 is byte-identical
in v2.0-v6.0 (same header CRC 0x51AA6C28) with four partitions; v7.0 ships pmtd 3.0.36 with five:

| partition | v2.0-v6.0 size | v7.0 size | inner tag | what it is (from the app's tags and menus) |
|---|---|---|---|---|
| PPCH | 0xBFEC | 0xBFEC | `LZ1M` | factory MEMORY patches (bank A) |
| PWD8 | 0xC7C | 0xC7C | `WDL8`/`BNK8` | 8-bit wave-memory banks |
| PWDG | 0x7530C | 0x7530C | `WFDT` | granular wave data |
| PPTN | 0x3ED8 | 0x451C | `SLST`/`E1SQ` | patterns / sequences |
| PPBB | - | 0xAFBC | `LZ1M` | second MEMORY bank (bank B), new with MEMORY BANK in v7.0 |

**Toolchain and runtime.**
- `lib_match.py` with CGT 8.3.2, 8.3.9, 8.3.13 and 8.5.0 `rts6740_elf.lib` (also `rts64plus_elf.lib`,
  `rts6600_elf.lib` for 8.3.2 and 8.3.13): 13 unique matches in v7.0 and 12 in v2.0, the same count for every version.
  The matches are hand-written assembly (`__divi`, `__divu`, `__remi`, `__remu`, `__strasgi_64plus`) plus two 32-byte
  functions (`exit` stub, `locale::__imp::make_global`). SmplTrek 3.2.174 against CGT 8.3.13 gives 146 unique. So the
  ELZ_1 C run-time was not built by any installed CGT; which CGT built it is not established (older than 8.3.2
  is likely, not shown).
- SYS/BIOS: `lib_match.py` with the scratch SYS/BIOS 6.76.03.01 build (a `sysbios.ae674`
  built from `analysis/sysbios_match.cfg`): 7 unique in v2.0 and v7.0 against 62 in SmplTrek. func_match
  pairs some kernel functions byte-identically with SmplTrek (hash 1.0: `Hwi_switchAndDispatch` 0xC11F2D40,
  `TaskSupport_buildTaskStack` 0xC11F5AE0, `Startup_exec` 0xC11E50A0, `Registry_findById` 0xC11F62A0; assembly or
  tiny functions). The static Task object is 76 bytes (stride of the table in B) where SmplTrek's is 92. The
  SYS/BIOS version is therefore not 6.76.03.01 as built, and not identified.
- C++: Itanium RTTI with `__cxxabiv1` type_infos; `std::exception`, `logic_error`, `length_error`,
  `out_of_range`, `type_info` are the only std classes (5, against 127 in SmplTrek). No `std::__2::__function`
  (lambda in `std::function`) type names, which SmplTrek and the Liven images have (raw strings).
- Device class: the decoded initialised data holds the SYS/BIOS timer table with two words each for Timer0
  0x01C20000, Timer1 0x01C21000, Timer2 0x01F0C000, Timer3 0x01F0D000 in all seven releases (scan of copy-table
  output), the DA850 form of INT-17. INT-17 says the legacy images were not covered; this covers them.

## B. SYS/BIOS static configuration

**Tasks** (`tasks.py`, `xrel.py`). Seven static Task objects of 76 bytes in initialised data
(v7.0 0xC1316170-0xC1316384): priority at +8, mode at +20, stack size at +28, stack at +32, fxn at +40 (field
offsets as in SmplTrek's 92-byte layout, `docs/01-platform-map.md` "Tasks"; they give consistent values here).
Six share fxn 0xC11F0B80 (the TaskHandler entry: `Task_self`, `Task_getEnv`, then the handler's vtable slot 0);
all have 2 KiB stacks at 0xC1080D90 + n*0x800; the seventh (fxn 0xC11FAC00, priority 0) is Idle. Handle globals
(initialised data, B14 + offset) and the priority each gets at run time from `Task_setPri` (0xC11BA060, by the
call sites listed):

| handler (TaskHandler subclass) | Task object | B14 offset | priority | set at |
|---|---|---|---|---|
| AsyncTaskHandler | 0xC1316170 | 1460 | 7 | 0xC11E7B00 |
| Foundation::ApplicationDelegate (ElizabethDelegate, main) | 0xC13161BC | 1480 | 1 (static) | bound at 0xC119A86C, then `BIOS_start` 0xC11FA900 |
| USBTaskHandler | 0xC1316208 | 1500 | 13 | 0xC11ED214 |
| FlashMemoryManager | 0xC1316254 | 1508 | 14 | 0xC116CED4 |
| Graphics::GraphicsManager | 0xC13162A0 | 1520 | 15 | 0xC116884C |
| OperatorObserver (key/encoder scan) | 0xC13162EC | 1528 | 15 | 0xC11C6C44 |
| Idle | 0xC1316338 | - | 0 | static |

Binding is `Task_setEnv` (0xC11FAD40, through 0xC11F0BC4). The six TaskHandler subclasses are exactly the RTTI
classes with base `TaskHandler`. The same seven objects and the same priority pattern (7, 13, 14, 15, 15 at B14
offsets n, n+40, n+48, n+60, n+68) are in all seven releases (`xrel.txt`; offsets mapped to handlers only in v7.0).

**Hwis, Swis, clock tick:** not settled (no time spent on the Hwi table or Clock period).

## C. Hardware use

Peripherals (`python3 -B analysis/hw_inventory.py "firmware/other/ELZ_1 v<v>.zip"`, `hw-<v>.txt`): INTC, cache
control, EDMA3 CC0, PSC0, PSC1, SYSCFG0/1, I2C0, SPI0, McASP0, USB0, LCDC, GPIO, eHRPWM (0x01F02000 = eHRPWM1); the
summary line is "parts with every peripheral found: C6748" in all seven (LCDC). The same peripheral list, with near-identical
site counts, in all seven (v4.0+ add one site at 0x01B77400, labelled "unknown", probably a non-address constant).
**Not found by this method in any release: MMC/SD (0x01C40000, 0x01E1B000), UART0/1/2, EMIFA, SPI1, I2C1,
McBSP, uPP, VPIF.** The decoded initialised data of v2.0 and v7.0 contains no word equal to an MMC/SD, UART, SPI1 or I2C1
base either (scan in this session); the timer table is the only peripheral data.

**CPU clock.** The LCD and SPI code divide a 186 MHz input clock (0x0B162280, built at 0xC11C1818/0xC11C1824 and
0xC118BD68/0xC118BD74; present in all seven): PLL0 SYSCLK2 = 186 MHz is CPU/2, so 372 MHz, the SmplTrek figure.

**LCD.** The LCDC is driven in LIDD (MPU-interface) mode, not raster. Init at 0xC11C17A4 (v2.0 0xC0DD23C4):
- PSC1 module 16 enabled (0xC11C17B4: `c11da200(0x01E27000, 16, ...)`), then a GPIO reset sequence;
- LCD_CTRL clock divider from 186 MHz / 15 MHz = 12 (0xC11C182C calls 0xC11D3A40, which divides and writes +0x4);
- LIDD_CTRL mode 3 = asynchronous MPU80 (0xC11D3914 with 3; writes +0xC);
- LIDD_CS0_CONF timing 0x00220045 (0xC11D3A58);
- MIPI DCS commands through LIDD_CS0_ADDR (0xC11C1698) and data through LIDD_CS0_DATA (0xC11C1768): 0x11 sleep
  out, 120 ms delay, 0x36 MADCTL with data 0x40, 0x3A COLMOD with data 0x5555 (16 bits/pixel), 0x29 display on.
  No CASET/RASET (0x2A/0x2B) call was found (only five command call sites, `packets.py --calls 0xC11C1698`);
- frame push 0xC11C16B0: command 0x2C (RAMWR), then the LCDC DMA streams one frame buffer through LIDD
  (FB0 base/ceiling written by 0xC11D3948, LIDD DMA enabled by 0xC11D3960, completion polled on LCD_STAT).
- Frame buffers (0xC1168480-0xC1168530, 0xC11E2E60): size 0x25800 = 153600 bytes, two of them at 0xC0F62D80 +
  n*0x25800 (index toggled at B14+1388). 153600 = 76800 pixels x 2 bytes (RGB565, matching COLMOD 0x55). Drawing
  code indexes rows of 480 bytes (293 `mpy` sites with 480, e.g. fill loop 0xC10A84B0-0xC10A8560, clip size
  {240, 320}): the frame buffer is **240 pixels per row, 320 rows**. Whether the panel is mounted portrait or
  landscape is not settled (MADCTL 0x40 sets only the column-order bit).
- The same command sequence, frequency constants and frame size in v2.0 (0xC0DD24B4-0xC0DD24EA) and in all seven
  by constant counts (`xrel.txt`: 0x01E13000 x9, 15000000 x1, 0x220045 x1, 153600 x7-11).
- Backlight (inference): the LCD on/off helper 0xC11C1680 writes a GPIO (0xC11E23EC) and branches to the eHRPWM
  routine 0xC11D79C8; eHRPWM1 is the only PWM addressed.

**Audio.**
- Sample rate 48 kHz: in v7.0 the code builds 48000 25 times, 48000.0f 151 times and 1/48000 79 times; 44100,
  44100.0f and 1/44100 zero times. Same picture in all seven (`xrel.txt`).
- McASP0 (base 0x01D00000) set up at 0xC116EE78 (from audio start 0xC116F090; PSC1 module 7 at 0xC116F0B0):
  serializer 0 transmit (0xC116EF90 -> 0xC115D124, SRMOD 1), serializer 1 receive (0xC116EF84 -> 0xC115D150, SRMOD 2);
  PDIR outputs AFSX, ACLKX, AXR0 (0x14000001, 0xC116EFAC) and inputs AFSR, ACLKR, AXR1 (0xA0000002, 0xC116EFC0);
  transmit bit clock internal, ACLKX = AHCLKX / 8 with AHCLKX taken from its pin (0xC116EF28 -> 0xC115D0A0,
  arguments 0x20/0/7/0, read against StarterWare `McASPTxClkCfg` field layout); receive clocks external
  (0xC116EEE8 -> 0xC115D414, all zero). So on ELZ_1 the DSP drives the transmit bit and frame clocks (from an
  external high clock), unlike SmplTrek where the codec is master (platform-map "McASP setup"). Inferred from
  register writes; the frame-sync width and slot format were not decoded.
- DMA: four EDMA PaRAM templates (0xC1391628-0xC13916A8): ACNT 4, BCNT 128 between the McASP DMA port 0x01D02000
  and ping-pong buffers in L1D RAM: transmit 0x11F00000/0x11F00200, receive 0x11F00400/0x11F00600, linked through
  PaRAM 64-67. A block is 128 32-bit words = 64 stereo frames (1.33 ms at 48 kHz). Identical templates in all seven
  (`xrel.txt`).
- Codec on I2C0: audio start sets the I2C slave address to 0x18 (0xC116F164 -> 0xC11AE390 with 24), the
  TLV320AIC310x address used by SmplTrek; I2C input clock 24 MHz (24000000 built at 0xC11AE3B4). The codec register
  writes and the codec part were not decoded.

**Input: DSP-side scanning, no panel MCU.**
- No UART is addressed (above), and the RTTI has no panel/AD-controller classes. The scan is a SYS/BIOS task
  (OperatorObserver, priority 15) whose loop (0xC11C6C8C-0xC11C6D60) steps a phase counter at B14+1408 through 16
  phases with a 1 ms delay (0xC11AC920(1)) and calls the switch scan, the keyboard scan and other pollers.
- `MusicalKeyboard` derives from `DynamicScan<unsigned long long, 5, 8>` (5 x 8 = 40 positions) and
  `ControlSwitch` from `DynamicScan<unsigned int, 4, 4>` (16). Their row hooks drive GPIO bank-pair output
  registers (0xC11E2404, OUT_DATA at 0x01E26014) and read GPIO input data (0xC11E2458, 0x01E26020): keyboard rows on
  bank 1 bit `row`, columns read from bank 5 (0xC11A90A0/0xC11A90A8); switch rows on bank 1 bit `row+12`, columns
  from bank 4 (0xC119B940/0xC119B948).
- Rotary encoders (`RotaryEncoder::Callback`, `TestRotaryEncoder`) and LEDs (`TestLED`, "> Turn on All LEDs", all
  seven) exist; how they are wired was not traced.

**Storage: SPI NOR flash with a FAT volume; no SD.**
- No MMC/SD controller is addressed in any release. SPI0 runs at 46.5 MHz (186 MHz / 4, 0xC118BD68) with EDMA
  channels 14/15. The FlashMemoryManager code (0xC116CEE4-0xC116D200) uses the SPI NOR protocol: read-status
  opcode 0x05 (halfword at 0xC139B990, loaded at 0xC116CEE4), busy poll on status bit 0 (0xC116CF54), block-erase
  opcodes 0xD8 (0xC116CFE8) and 0x52 (0xC116D0C4), 4-byte command headers (opcode + 24-bit address), so a device of
  at most 16 MiB with 3-byte addressing (inferred).
- FatFs is linked (`FAT`/`FAT32` 0xC10A2A94, `NO NAME    FAT32   ` volume-label strings used by the mkfs code at
  0xC10A6BD0). STORAGE menu: "Capacity" is the constant string "8.00MB" when the volume is present and "0.00B"
  otherwise (MenuStorage function 0xC1123F88, returns one of the two after 0xC1190CB8(0)); "Free Space" is formatted
  by the next function (0xC1123FAC). So the user volume is presented as 8 MB. Present in all seven (raw strings).
- The volume is exported to a computer as USB mass storage ("USB MASS STORAGE MODE"; SCSI inquiry
  "SNCWR   ELZ_1           1.00" at 0xC1393180, all seven).
- The SYSTEM INFORMATION page shows BOOT, PRESET and SYSTEM versions (strings at 0xC1126768-0xC1127130) read from
  a run-time table of image headers at 0xC10A0400 (four entries searched for the tags `bmtd`/`pmtd`/`mmtd` at
  0xC11A100C-0xC11A10C4; "*.*.*" when missing). Who fills that table was not traced.

**USB.** USB0 is addressed from 73 functions (`hw-7.0.txt`). Decoded initialised data (`usb2.py`) holds two
device descriptors (0xC1318B00, 0xC1318B18: USB 2.0, class 0, EP0 64, VID/PID 0 at load, filled at run time as in
SmplTrek; string indexes 1/2/3 and 1/2/0) and two configuration headers: 32 bytes / 1 interface (mass storage shape:
9+9+7+7) and 86 bytes / 2 interfaces (Audio Control + MIDI Streaming with 64-byte bulk endpoints 0x81/0x01 and
MIDI jack descriptors nearby). No USB audio streaming interface was found. Menus offer "MIDI DEVICE MODE" and
"MIDI HOST MODE" (USB host, "Please Check USB Host Cable.", `TestUSBHost`). Same descriptors in all seven.

**MIDI.** USB only, as far as this method sees: there is no UART for DIN MIDI. Settings pages for RX/TX
channel (TX channel from v4.0), MIDI THRU, MIDI clock out and clock source (v4.0+) and USB MIDI; MIDI monitor strings ("N-On  c:", "PC c:", "CC c:").
No SysEx-related class or string was found; whether the parser handles SysEx was not checked.

**Sync.** `MenuSyncInGain` ("SYNC IN GAIN", all seven) and `MenuSyncOut` / "SYNC OUT" (from v4.0); with no further timer or
GPIO trace the sync path is not settled (the gain setting suggests the sync input goes through the codec ADC;
inference).

**Power.** `PowerManager::DataSource`, AUTO POWER OFF with 30 minutes / 1 hour / 3 hours / 6 hours, "Shutting
down...", `TestBatteryLevel` / "Battery Level". The battery measurement path was not traced (the C6748 has no ADC).

## E. Formats and protocols visible in code

- **User volume layout** (directory and extension table, initialised data 0xC139DC90, all seven via `xrel.py`):
  `MEMORY` + `*.e1m` (patches), `WAVEDATA` + `*.wav`, `SEQUENCE` + `*.e1p` (patterns), `BACKUPDATA` + `*.ebk`
  (backups). The app checks each is a directory ("MEMORY is not a directory." 0xC114CA24 and the WAVEDATA, SEQUENCE,
  BACKUPDATA equivalents). Default names: "PATTERN000", "WAVEDATA0", backup "ELZ_1_USERDATA" (`ArchiveSave` vfunc
  0xC11F6980 copies it into the object).
- **Patch (MEMORY) format**: chunk tag `LZ1M` (code ref 0xC10D84C4) with sub-tags seen next to it in code
  (`PTNM`, `MODS`, `OCTV`, `OSCR`, `OSCM`, `FLTR`, `FLTM`, `LVL `, `PSTG`, `VCMD`, `WVMD`, `ARPG`, effect tags
  `EDLY`/`EDRV`/`EMOD`/`ERVB`/`EVLP`). The factory partitions PPCH and PPBB start with the same tag, so the
  factory memories use the patch format. Field layout not decoded.
- **Wave memory**: `WDL8` / `BNK8` (PWD8 partition), `FM8B`. **Granular wave data**: `WFDT` (PWDG partition).
- **Patterns**: `SLST` / `E1SQ` (PPTN partition), `SEQN` / `SEQT` (code refs 0xC11788B0, 0xC1178C90).
- **Backup archive** (`*.ebk`): tag `ARCV` with sections `APCH`, `APBB` (v7.0), `AWD8`, `AWDG`, `ASEQ` (code refs
  0xC10C004C-0xC10C06C8), i.e. one record per preset partition kind.
- **Settings** (`PREF`, written to flash by FlashMemoryManager, inference from the class and tag code refs in
  0xC1101290-0xC1101D94, one setter/getter per tag): MSTT, MEMT, TNMD (2.1), AFXI, MODS (3.0), CSRC, EBPM, MCKO,
  MTCH, MUSB, SCKO (4.0), AX1G/I/P/S, AX2G/I/P/S, AXIG, AXIM, AESD (5.0), MBNK (7.0), plus APWR, MRCH, MTHR, MEM ,
  MTVL, PTRN, SQMD, SCKG.
- **WAV files**: `RIFF`/`WAVE`/`fmt `/`data`/`LIST`/`INFO`/`ICMT` and a private `LoFM` chunk
  (`LobitFMWaveFile`, refs 0xC1159880-0xC1159C30), filter "*.wav"; "Invalid Audio Format" on import.
- **Updates**: the app contains no update, SysEx or file-name-of-update strings (raw strings of all seven). Updates
  are a bootloader function: BOOT 1.0.10 in v6.0 updates over USB mass storage or USB HID (`docs/05-bootloader.md`
  last section). The app only displays the three image versions.

## G. Relation to ELZ_1 play and SmplTrek

- **Class names** (`rtti_recover.py` lists, this session): ELZ_1 v7.0 shares 173 of its 289 classes with ELZ_1 play
  3.1.149 (179 with play 1.1.62), 65 with Liven 8bit warps 1.1.62, 51 with Liven Lofi-12 2.1.65, 45 with SmplTrek
  3.2.174 and 39 with Lofi-12 XT 1.5.205. The shared set with ELZ_1 play covers nearly the whole UI (UI::*, Menu*
  pages, AUX dialogs, launch animations), the effects, the archive/patch/sequence import-export classes and the
  test-mode classes: ELZ_1 play's application layer descends from ELZ_1's.
- What ELZ_1 has that play does not: the DSP-side scan classes (DynamicScan, MusicalKeyboard, ControlSwitch),
  `FlashMemoryManager`, the polymorphic `TaskHandler` with six subclasses, `ElizabethDelegate`, the
  `OSCGenerator`/`OSCObject` template engine (also in Liven 8bit warps, not in play), PowerManager/StatusBar.
- **Code**: func_match carries only 82 pairs from SmplTrek 3.2.174 and 283 from ELZ_1 play 3.1.149 into ELZ_1 v7.0
  (most of them SYS/BIOS, RTS and assembly; several carried names have similarity below 0.4 and were not used). The
  shared classes are therefore same-design, not the same compiled code; with the different C compiler (A) a
  byte-level match was not expected.
- **Platform lineage** (summary): same C6748 at 372 MHz, same codec I2C address 0x18, same SYS/BIOS DA850 timer
  configuration and the same bootloader codebase (`[ELZ_1]$` prompt in SmplTrek's BOOT, INT-15) as the SmplTrek
  family; but no SD (SPI NOR flash with a FAT volume), no panel MCU (GPIO matrix scan), an LCDC-driven LIDD panel
  of 240 x 320 RGB565, USB-only MIDI, a 64-frame audio block in L1D RAM, and transmit clocks generated by the DSP.

## Not settled

- Codec register writes and part; McASP frame-sync and slot format; whether AHCLKX is the codec MCLK.

## Tool notes

- `memory_map.py` on a legacy image: "copy table (__TI_auto_init) not found". The legacy `__TI_auto_init` keeps a
  3-entry handler table 0x28 bytes before the records (v7.0: 0xC141B418 / 0xC141B440), which fails the tool's
  `B - H <= 16` test; the same constants in every release (`inits.txt`). Decoding works (`copytab.py`),
  so hw_inventory's data-word scan and INT-17 could cover the legacy images.
- `string_refs.py` misses pointers that live only in compressed initialised data (e.g. the directory table at
  0xC139DC90: `*.e1m`, `*.e1p`, `*.ebk` report no references), and its per-release reference sets flicker (e.g.
  "MIDI HOST MODE" is present in v7.0 but reported unreferenced), so release diffs were made from raw presence.
- `rtti_recover.py` used "frequency fallback (unverified kinds)" for the ABI vptrs on ELZ_1 although the three
  `N10__cxxabiv1..._type_infoE` names are in the image; the `.rtti.err` files ("size mismatch or unsupported
  legacy layout") are older than the JSON and stale.
- `func_match.py` carried names with similarity 0.0-0.13 (`prex_ext_track_settings`, `memset`, `f_mkfs`) onto
  ELZ_1; none was relied on.
